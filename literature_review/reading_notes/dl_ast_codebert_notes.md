# Deep learning on ASTs / token sequences / CodeBERT for defect prediction — reading notes
Group: DL-AST-token-CodeBERT + two surveys. Read in full: Wang 2016, DP-CNN 2017, Dam (arXiv preprint substitute for MSR'19), Pan 2021, Giray 2023 SLR, Li 2024 survey. Abstract only: DH-CNN (TR 2024), DeepLineDP (TSE 2022).

## Wang, Liu & Tan, 2016, Automatically Learning Semantic Features for Defect Prediction, ICSE 2016
DOI: 10.1145/2884781.2884804 — access: **full_text**
- **Task and granularity**: Binary file-level defect prediction (buggy/clean), within-project (WPDP, actually cross-version) and cross-project (CPDP).
- **Language and data**: Java only. 10 PROMISE projects with source retrieved by version (Table 1): ant 1.5/1.6/1.7, camel 1.2/1.4/1.6, jEdit 3.2/4.0/4.1, log4j 1.0/1.1, lucene 2.0/2.2/2.4, xalan 2.4/2.5, xerces 1.2/1.3, ivy 1.4/2.0, synapse 1.0/1.1/1.2, poi 1.5/2.5/3.0. Average files per project 150-1,046; average buggy rate 13.4%-49.7% (Sec 4.2, Table 1). Labels are the PROMISE post-release labels.
- **Representation**: Token sequence from Java ASTs (parser not named in the text read): three node categories kept — method invocations/class instance creations (by name), declarations (method/type/enum), control-flow nodes (if, while, catch, throw... recorded by type) (Sec 3.1). For CPDP, names replaced by node types. Tokens occurring <3 times dropped; tokens mapped to integer IDs, zero-padded to longest vector, min-max normalised (Sec 3.2-3.3). No CFG/DFG.
- **Model**: Deep Belief Network (stacked RBMs, unsupervised) trained on the training-version token vectors; 10 hidden layers x 100 nodes, 200 iterations (Sec 4.4); 100 DBN outputs used as features for ADTree (main), Naive Bayes, Logistic Regression. CPDP variant DBN-CP uses ADTree.
- **Baselines**: (1) 20 PROMISE static metrics (LOC, CK, McCabe, Halstead-type) with the same classifiers; (2) bag of AST-node term frequencies; (3) for CPDP, TCA+ re-implemented by the authors on PROMISE metrics.
- **Evaluation setup**: WPDP = consecutive-version split: older version trains, newer version tests, 16 pairs (Sec 4.5, Table 2). CPDP = 22 source/target pairs chosen randomly across projects (Sec 4.6). SMOTE on training data only (Sec 4.5). CLNI edit-distance noise removal applied to the data (Sec 3.2.1); the text does not say whether test instances were excluded from this cleaning. DBN hyperparameters were chosen by average F1 on ant 1.5->1.6, camel 1.2->1.4, jEdit 4.0->4.1, lucene 2.0->2.2, poi 1.5->2.5 (Sec 4.4), which are also evaluation pairs. DBN run 5 times; outputs identical (Sec 5, RQ1).
- **Duplication or leakage handling**: Not discussed. The paper does not mention duplicate or unchanged files between consecutive versions. Two leakage-like issues are present: hyperparameters were tuned on evaluation pairs (Sec 4.4), and CLNI label-noise removal may have modified the test sets (Sec 3.2.1/4.3; not stated).
- **Metrics and key results**: Precision, recall and F1 only. WPDP with ADTree, average over 16 pairs: semantic F1 64.1 vs PROMISE metrics 49.9 vs AST-TF 44.7 (Table 2); precision/recall 63.0/70.7 vs 48.3/59.2. NB: 60.0 vs 45.2; LR: 59.7 vs 49.0 (Table 3). Some single pairs are extreme, e.g. ant 1.6->1.7 F1 94.2 vs 54.2 (Table 2). CPDP average F1: DBN-CP 56.8 vs TCA+ 47.9; WPDP reference 63.2 (Table 4). Feature-generation time 8.0-32.0 s, memory <6.5 MB (Table 5).
- **Stated limitations**: TCA+ was re-implemented (original not released). The 10 projects may not generalise. Only open-source Java was evaluated (Sec 6).
- **Critical assessment**: This is the paper the later literature builds on, and its evidence is weak. (i) Hyperparameters were selected on test pairs, so the results are optimistically biased. (ii) Only threshold-dependent F1/P/R are reported: no AUC, MCC or effort-aware measures, no statistical tests, no variance. (iii) Categorical token IDs are fed to the DBN as min-max-scaled continuous values, which imposes an arbitrary ordinal structure; the method's success is hard to explain mechanistically. (iv) Baselines are weak: ADTree/NB/LR on 20 PROMISE metrics, with no RF or tuned learners and no process metrics. (v) Small datasets (150-1,046 files). (vi) No code release is mentioned, and DP-CNN (QRS'17) had to re-implement DBN after emailing the authors. (vii) The near-perfect F1 on ant 1.6->1.7 (94.2) and the CPDP camel1.4->ant1.6 result (97.9) exceeding WPDP were not investigated. One plausible cause is that many files are unchanged between versions, so a test file can carry the same token sequence as a training file; the paper does not check for this.
- **Relevance to project**: This is the origin of the 'consecutive-version' protocol that the project's CVDP setup inherits. It is a direct precedent for comparing learned code features with metric baselines (analogous to SonarQube metrics) under cross-version splits. It is also a prime example of an unchecked identical-file risk: the project's duplicate/unchanged-code leakage analysis could be framed against this protocol. The representation (AST token bag/sequence) is weaker than Joern CFG+DDG, and the file granularity differs from the project's per-function graphs. Java only.

## Li, He, Zhu & Lyu, 2017, Software Defect Prediction via Convolutional Neural Network (DP-CNN), QRS 2017
DOI: 10.1109/qrs.2017.42 — access: **full_text**
- **Task and granularity**: Binary file-level defect prediction; within-project consecutive-version setting only.
- **Language and data**: Java only. 7 tera-PROMISE projects, one train->test pair each (Table I): camel 1.4->1.6, jEdit 4.0->4.1, lucene 2.0->2.2, xalan 2.5->2.6, xerces 1.2->1.3, synapse 1.1->1.2, poi 2.5->3.0. On average 330 files per project and a 35% buggy rate (Sec IV-B); per-project average buggy rates range from 15.5% (xerces) to 64.7% (poi) (Table I). Source code was matched from GitHub by class name.
- **Representation**: Java AST parsed with javalang. The same three node categories as Wang et al. 2016 (invocations/instance creations by name, declarations, control-flow node types; full list in Fig. 5). Tokens with fewer than 3 occurrences are zeroed; sequences are integer-encoded and zero-padded (Sec III-A/B). No CFG/DFG.
- **Model**: 1-D CNN in Keras: trainable embedding (dim 30), one conv layer (10 filters, length 5), max-pooling, a 100-unit dense layer, and a logistic output. DP-CNN concatenates the CNN features with the 20 PROMISE metrics before the logistic output (Sec III-C, IV-F). Batch 32, 15 epochs, Adam.
- **Baselines**: Traditional: LR on 20 PROMISE metrics. DBN: the authors' re-implementation of Wang et al. 2016. DBN+: DBN plus metrics. CNN: DP-CNN without metrics (Sec IV-C).
- **Evaluation setup**: Cross-version: older version trains, newer version tests, 7 pairs. Training-set minority oversampling by duplicating buggy files (training only, Sec III-B2). Each experiment run 10 times and averaged (Sec IV). CNN hyperparameters (filters, filter length, hidden nodes) were chosen by F-measure on camel, xalan and xerces, which are evaluation pairs (Sec IV-F, Fig. 8). No separate validation set is described.
- **Duplication or leakage handling**: Not discussed. Unchanged files between consecutive versions are not addressed. Hyperparameters were tuned on 3 of the 7 test pairs (Sec IV-F).
- **Metrics and key results**: F-measure only (Sec IV-A). Average F1 over the 7 pairs (Table II): Traditional 0.524, DBN 0.543, DBN+ 0.559, CNN 0.596, DP-CNN 0.608. DP-CNN is best on 6/7 pairs (jEdit is the exception: CNN 0.631 vs DP-CNN 0.580). The headline claims improvements of 16%, 12% and 2% over Traditional, DBN and CNN (Sec IV-E). Strongest baseline: CNN 0.596. Metrics added only +0.012 on average.
- **Stated limitations**: DBN was re-implemented (the original was not released, and details such as the full AST node list and learning rate are missing). Only 7 Java PROMISE projects (Sec V).
- **Critical assessment**: Weak evidence. Seven pairs, F1 only, with no variance despite 10 runs, no statistical tests, and tuning on test pairs. The 'Traditional' baseline is a single LR on 20 metrics. The re-implemented DBN numbers differ from those Wang et al. reported for the same pairs (e.g. lucene 2.0->2.2: 0.758 here vs 65.1 F1 with ADTree in Wang Table 2; camel 1.4->1.6: 0.335 vs 37.4). The differences cannot be resolved from the text read (different classifier, LR here) and show how fragile these numbers are. The text read describes no code release. The improvement of DP-CNN over CNN (0.012 F1) is within the noise one would expect at these sample sizes.
- **Relevance to project**: Supplies the 7 'standard' consecutive-version PROMISE pairs later reused by Pan et al. 2021 for CodeBERT, so it is the reference point for CodeBERT-vs-earlier-DL comparisons. Its finding that concatenating hand-crafted metrics with learned features adds little (+0.012 F1) is relevant to combining graph embeddings with SonarQube metrics. It shares Wang et al.'s protocol risks (no unchanged-file control, test-set tuning). It is not graph-based.

## Dam, Pham, Ng, Tran, Grundy, Ghose, Kim & Kim, 2019, Lessons Learned from Using a Deep Tree-Based Model for Software Defect Prediction in Practice, MSR 2019 (read via arXiv:1802.00921 preprint 'A deep tree-based model for software defect prediction', 2018)
DOI: 10.1109/msr.2019.00017 — access: **full_text**
- **Task and granularity**: Binary file-level defect prediction; within-project (10-fold CV and consecutive-version) and cross-project.
- **Language and data**: (a) Samsung (Tizen-related) open-source C code: 8,118 files, 2,887 (35.6%) labelled defective (Sec 6.1). Labels come from an undisclosed internal static-analysis tool: a file is 'defective' if the tool reported at least one critical resource-leakage warning, not from real bugs. (b) The same 10 PROMISE Java projects/versions as Wang et al. 2016 (Table 1: e.g. camel 3 versions, 2,379 files, 24.54% defective; ivy 9.00%; poi 63.14%). 264 PROMISE entries were removed (inner classes, Scala files, unretrievable files).
- **Representation**: Full AST of each file; each node is labelled by its AST type or by token for names, constants are mapped to type, and rare tokens become <unk> (Sec 4.1). Node embeddings ('ast2vec') feed a tree-structured LSTM whose topology mirrors the AST. Parser not named in the text read; Java node names suggest JavaParser. No CFG/DFG.
- **Model**: Child-sum Tree-LSTM trained unsupervised, predicting each parent node's label from its children (Sec 5.1). It is tuned with RMSprop and early stopping on a validation split, with dropout. The resulting file vectors feed a separately trained Random Forest or Logistic Regression (Sec 5.2).
- **Baselines**: No re-run baselines. For PROMISE, results are compared with the numbers Wang et al. 2016 reported (DBN), because the authors could not replicate them (Sec 6.4).
- **Evaluation setup**: Samsung: stratified 10-fold CV over all files treated as one project, i.e. a random split (Sec 6.3.1). PROMISE: 16 consecutive-version pairs exactly as Wang et al. (older trains, newer tests). CPDP: 22 source/target pairs (Sec 6.3.2). The language-model training split is 'mutually exclusive training, validation and test sets' (Sec 5.1), but how this relates to the defect-classifier split is not detailed. No resampling is described.
- **Duplication or leakage handling**: Not discussed. The Samsung random 10-fold CV places files from the same projects (and potentially near-duplicate files) in train and test. Labels are generated by a deterministic static analyser, so the model may learn to reproduce the analyser's syntactic triggers.
- **Metrics and key results**: Precision, recall, F-measure and AUC. Samsung with RF: all four measures 'well above 0.9', AUC 0.98; LR has AUC 0.60 (the text says '0.60 for RF', an evident typo) (Sec 6.3.1, Fig. 6). PROMISE with LR (only LR reported): average AUC 0.6 and average recall 0.86. Recall is 23% higher than Wang et al., but F-measure is 17% lower because of low precision (Sec 6.3.1, Fig. 7). CPDP: average recall 0.8 and average F-measure 0.5 over 22 pairs; AUC reported only as 'well above 0.5' (Sec 6.3.2, Fig. 8). Per-pair values are given only in figures. Strongest baseline: Wang et al.'s reported DBN F1 (higher F1).
- **Stated limitations**: Samsung labels are static-analysis warnings that may contain false positives. Wang et al.'s experiments could not be replicated, so the comparison relies on reported numbers. No statistical tests were run (planned as future work). Generalisability to other application types and languages is untested (Sec 6.4).
- **Critical assessment**: Read via the arXiv preprint; the MSR'19 published version adds 'lessons learned' sections that I could not read, so those are not covered here. The headline Samsung result (AUC 0.98) is not evidence of defect prediction: the labels are resource-leak warnings from a rule-based tool, the split is random 10-fold, and a Tree-LSTM over ASTs can plausibly learn the tool's syntactic patterns. On real PROMISE labels the model reaches only about 0.6 AUC with lower F1 than DBN, which undercuts the claim that tree-structured DL beats simpler approaches. The comparison against numbers reported elsewhere is not a controlled comparison. No metric baseline was run, there is no variance and no tests, and the text read describes no code release.
- **Relevance to project**: Mainly a cautionary example. It shows how random CV and tool-derived labels inflate results, which bears on the project's leakage analysis and on using SonarQube-derived signals. On real labels in a cross-version setting, the structure-aware AST model gives modest AUC (~0.6). That is a realistic prior for what structural code models may achieve on Django/ActiveMQ CVDP. Its use of a structural (tree) neural model is the closest in spirit to graph-based (Joern CFG/DDG) models among the token/AST papers.

## Pan, Lu & Xu, 2021, An Empirical Study on Software Defect Prediction Using CodeBERT Model, Applied Sciences 11(11):4793
DOI: 10.3390/app11114793 — access: **full_text**
- **Task and granularity**: Binary file-level defect prediction; cross-version (CVPSC) and cross-project (CPPSC).
- **Language and data**: Java PROMISE source. CVPSC: 7 consecutive-version pairs identical to DP-CNN's pairs (camel 1.4->1.6, jEdit 4.0->4.1, lucene 2.0->2.2, xalan 2.5->2.6, xerces 1.2->1.3, synapse 1.1->1.2, poi 2.5->3.0); 6,549 files, 2,299 defects, average buggy rate 35.1% (Table 1). CPPSC: 9 cross-project pairs, 8,589 files, 39.6% (Table 2).
- **Representation**: Raw source text with comments removed, tokenised by CodeBERT's word-piece/BPE tokenizer. Three input 'prediction patterns': traditional (code only), sentence (code + 'The code is buggy'), keyword (code + 'bug, defect, error, fail, patch') (Sec 4.2-4.4). The maximum sequence length/truncation is not reported, although CodeBERT accepts at most 512 tokens, so most files must have been truncated. No AST/CFG/DFG.
- **Model**: Fine-tuned CodeBERT (HuggingFace) with a classification head: CodeBERT-PT (pre-trained, traditional), -PS (sentence), -PK (keyword), and -NT (same architecture trained from scratch). lr 1e-5, batch 32, max 20 epochs, threshold 0.5 (Sec 4.6-4.7). The architecture description is internally inconsistent: it says 'RoBERTa-large' and also 'six layers, 768-dim, 12 heads'.
- **Baselines**: Only CodeBERT variants and a RANDOM classifier. The authors explicitly exclude AST/CFG/metric-based models as 'inappropriate' to compare (Sec 5.3).
- **Evaluation setup**: Cross-version (older->newer) and cross-project pairs. Random oversampling of the training set to 50/50 (Sec 4.5). '5-holdouts repeated experiments' (Sec 5). Hyperparameters were tuned and early stopping performed ON THE TEST SET (Sec 4.6: 'We tune hyperparameters and perform early stopping on the test set'). The best F1 across multiple runs is reported (Sec 5.1: 'We perform multiple experiments to find the experimental results with the best performance, i.e., best F1 values').
- **Duplication or leakage handling**: Not discussed. Unchanged files across versions are not addressed. Direct test-set leakage exists through test-set early stopping/tuning and best-of-runs reporting. Possible pre-training contamination (Apache Java code in CodeBERT's CodeSearchNet corpus) is not discussed.
- **Metrics and key results**: F1 is the main metric. G-measure, AUC and MCC are said to be in online supplementary data, not in the paper. Cross-version average F1 (Table 3): CodeBERT-NT 0.544, CodeBERT-PT 0.565, RANDOM 0.397. Sentence/keyword patterns (Table 5): PS 0.616, PK 0.613. Cross-project average F1 (Table 4): NT 0.51, PT 0.519, RANDOM 0.402; PS 0.57, PK 0.551 (Table 6). Pre-trained training reportedly converges 4x (CV) and 1.5x (CP) faster than training from scratch (Sec 6.2). Keyword analysis: files containing 'error' (654 samples) have a 49.8% buggy rate vs the 35.1% average (Table 7). Cross-paper observation (mine, not the authors'): on the same 7 version pairs DP-CNN reported 0.608 and CNN 0.596 average F1 (DP-CNN Table II), above plain CodeBERT-PT's 0.565. Setups differ (file counts, protocol), so the comparison is indicative only.
- **Stated limitations**: Java PROMISE only (the method is claimed language-agnostic). Dataset is a PROMISE subset. Only standard CodeBERT is used, not GraphCodeBERT (Sec 8).
- **Critical assessment**: Very weak evidence despite being the commonly cited 'CodeBERT for SDP' study. (i) Test-set early stopping/hyperparameter tuning plus best-of-N reporting invalidate the absolute numbers. (ii) The only baseline is RANDOM, with no metrics model, no DBN/CNN, and no frozen-embedding + classical-learner baseline. (iii) Truncation to CodeBERT's input limit is unreported. (iv) No variance or statistical tests; the PT vs NT gaps are 0.021 and 0.009 F1. (v) The PS/PK gain is attributed to 'understanding' the prompt, yet with a fixed constant sentence appended to every input it is unclear how this can add information. The authors' own Table 7 suggests lexical keyword cues ('error', 'patch') correlate with labels, a shortcut rather than semantics. (vi) Architecture description inconsistent. Data is on gitee; code availability is unclear from the paper. Even under these favourable conditions, plain CodeBERT does not clearly beat earlier AST-CNN results on the same pairs.
- **Relevance to project**: This is the main prior evidence for a CodeBERT baseline in cross-version defect prediction, which the project already runs. It shows (a) the reported CodeBERT gains are small and methodologically compromised; (b) fair comparison needs a validation version (not the test version) for early stopping, and the 512-token truncation must be reported, which matters less for the project's function-level units; (c) a lexical-shortcut check (keywords/identifiers) is warranted, related to the project's doc2vec baseline; and (d) no study here compares CodeBERT with CFG/DDG graph models or controls for unchanged code, which is the project's gap. Java only; no Python.

## Abdu, Zhai, Abdo & Algabri, 2024, Software Defect Prediction Based on Deep Representation Learning of Source Code From Contextual Syntax and Semantic Graph (DH-CNN), IEEE Transactions on Reliability 73(2)
DOI: 10.1109/tr.2024.3354965 — access: **abstract_only**
- **Task and granularity**: Per abstract: software defect prediction under within-project and cross-project scenarios. The granularity is not stated in the abstract (secondary sources describe file-level).
- **Language and data**: Not available from the abstract; not reported here.
- **Representation**: Per abstract: (1) syntax features from ASTs embedded with Word2vec; (2) 'semantic-graph' features from the control flow graph (CFG) and data dependence graph (DDG) embedded with Node2vec. The extraction tool is not given in the abstract.
- **Model**: Per abstract: deep hierarchical CNN (DH-CNN) with a syntax-level branch and a semantic-level branch, plus a gated merging mechanism that learns the combination ratio of the two feature types.
- **Baselines**: Not available (abstract says only 'existing methods'). One secondary source lists DBN among the comparators.
- **Evaluation setup**: Per abstract: cross-project and within-project scenarios; details unavailable.
- **Duplication or leakage handling**: Unknown (full text not read).
- **Metrics and key results**: Abstract claims DH-CNN 'outperforms existing methods' under CPDP and WPDP; no numbers are available.
- **Stated limitations**: Unknown (full text not read).
- **Critical assessment**: Could not be assessed. The full text is paywalled; no open copy was found by publisher, Unpaywall, Semantic Scholar or web search. A 2026 diagnosis paper (ScienceDirect, 'Has cross-project defect prediction truly progressed?') groups DH-CNN among recent CPDP methods whose claimed superiority it questions; I read only its search snippet.
- **Relevance to project**: Potentially the most directly relevant paper in this group: it uses CFG+DDG (the same graph types as the project's Joern output) and combines them with AST features. It should be obtained through institutional access and read for its graph extraction tool, split type, baselines and leakage handling before it is cited as evidence.

## Giray, Bennin, Köksal, Babur & Tekinerdogan, 2023, On the use of deep learning in software defect prediction (SLR), Journal of Systems and Software 195:111537
DOI: 10.1016/j.jss.2022.111537 — access: **full_text**
- **Task and granularity**: Systematic literature review of DL for SDP (all granularities and scenarios).
- **Language and data**: 102 primary studies published up to 31 Dec 2021, from 5 databases (296 candidates), plus manual and forward snowballing and a quality threshold (Sec 3.2, Table 3). The most-used datasets are PROMISE Java projects (Camel in 55 studies, Xalan 53, Xerces 49...) and NASA C/C++ sets; all datasets used in ≥10 studies are Java, C or C++ (Sec 4.3, Table 6).
- **Representation**: Survey findings (Sec 4.4): 67 studies used metrics; 38 used ASTs; 40 used some intermediary representation (AST, assembly, CFG, PDG, DFG, image); 8 combined metrics with an AST-type representation. CFG/PDG/DFG use is rare (e.g. Phan et al. 2017 CFGs from assembly; Li et al. 2019b PDG/DFG).
- **Model**: Survey findings (Sec 4.7): CNN is most frequent, followed by RNN/LSTM/GRU, MLP and DBN; 13 encoder-decoder/autoencoder studies; GNNs rare.
- **Baselines**: n/a (survey). Section 5.1 states that DL improvements were 'not significant when compared to traditional ML models', a qualitative synthesis without meta-analysis.
- **Evaluation setup**: Survey findings: 82 studies WPDP, 42 CPDP, 22 both; only 10 studies cross-version (Sec 4.1). 60 used hold-out and 43 cross-validation (Sec 4.8). 63 used data-level imbalance handling (42 oversampling, 21 SMOTE); 42 reported none (Sec 4.6). The survey does not record whether resampling touched test data.
- **Duplication or leakage handling**: Not discussed. The words leakage, duplicate code and unchanged code do not appear as analysis topics ('duplicate' appears only for removed search duplicates and in describing oversampling).
- **Metrics and key results**: Evaluation metrics (Sec 4.8): F-measure in 69 studies (68%), recall 48, AUC 40, precision 40, accuracy 28, MCC 20, effort-aware measures 13 (Popt 6, PofB20 4), G-measure 9. Reproducibility (Sec 4.9): 11 studies (11%) gave data + scripts, 36 data only, 2 scripts only, 4 broken links, 49 (48%) nothing. File-level 37 studies, module 32, change 12, function/statement 3 each (Sec 4.5).
- **Stated limitations**: Covers literature to end-2021 only. Grey literature (arXiv-only) excluded. No backward snowballing. Researcher bias in inclusion and open coding. Quality assessment was done by one author per paper (Sec 5.2).
- **Critical assessment**: A useful quantitative map but shallow on validity. It has no meta-analysis of effect sizes and does not code whether hyperparameters were tuned on test data, whether resampling leaked, or whether splits were time-ordered. Its 2021 cut-off means no transformer/CodeBERT studies are covered ('BERT' does not appear). Some recommendations (convert code to images for privacy and augmentation) are speculative. The figures on F1 dominance, rare MCC and rare replication packages are the most reusable facts.
- **Relevance to project**: Gives citable numbers for (a) how rare cross-version DL studies are (10/102) and how rare CFG/DFG/PDG representations are; (b) the dominance of F1 and rarity of MCC/effort-aware metrics, which supports reporting MCC, AUC and effort-aware measures; (c) the low share of full replication packages (11%), which motivates releasing the Joern pipeline; and (d) the absence of Python datasets among commonly used ones, which supports Django as a gap. Silent on leakage/duplicates, so the project's leakage analysis is not covered by this SLR.

## Li, Niu & Jing, 2024, Software defect prediction: future directions and challenges, Automated Software Engineering 31:19
DOI: 10.1007/s10515-024-00424-1 — access: **full_text**
- **Task and granularity**: Short position/vision paper (14 pp.) on SDP in general; no experiments.
- **Language and data**: None (no empirical data).
- **Representation**: Discussed only. Direction 3 ('multi-feature fusion') argues for fusing multiple representations (AST, CFG, call-flow graph, DFG, PDG, token embeddings) and for combining hand-crafted metrics with semantic features (Sec 3.2).
- **Model**: n/a
- **Baselines**: n/a
- **Evaluation setup**: n/a. The paper describes a generic pipeline (data cleaning including 'removing duplicate instances' citing Shepperd et al. 2013; metric selection; normalisation; imbalance handling) (Sec 2).
- **Duplication or leakage handling**: Mentions removing duplicate instances only as a generic data-cleaning step (Sec 2, citing Shepperd et al. 2013). Train/test leakage, unchanged code across versions and cross-version evaluation are not discussed.
- **Metrics and key results**: No results. It recommends AUC, MCC, F1 and effort-aware PofB@20%, PMI@20% and IFA (Sec 2), and use of actual effort rather than LOC as the effort proxy (Direction 7). The 8 directions are: label quality/SZZ, privacy-preserving sharing, multi-feature fusion, line-level prediction, robust/tuned models, unsupervised SDP, actual effort, explainability/actionability (Fig. 2, Sec 3).
- **Stated limitations**: Not exhaustive; the authors do not claim generality of their ideas (Sec 4).
- **Critical assessment**: An opinion piece with no new evidence. It does not mention pre-trained code models, leakage or evaluation-protocol validity (time-ordered splits, duplicates), arguably the most pressing DL-SDP issues. It is useful only as a recent citation for the multi-representation fusion direction and the recommended metric set.
- **Relevance to project**: Citable support for (a) fusing tree- and graph-based representations with metrics (CFG+DDG + SonarQube); (b) reporting MCC/AUC plus effort-aware measures; and (c) duplicate removal as part of data cleaning. The leakage gap the project addresses is absent here, which reinforces its novelty.

## Pornprasit & Tantithamthavorn, 2023 (online 2022), DeepLineDP: Towards a Deep Learning Approach for Line-Level Defect Prediction, IEEE TSE 49(1):84-98
DOI: 10.1109/tse.2022.3144348 — access: **abstract_only**
- **Task and granularity**: Per abstract: file-level and line-level defect prediction (risk ranking of lines within predicted-defective files), plus a practitioner survey (36 respondents).
- **Language and data**: Per abstract: 32 releases of 9 software projects. Per the replication README (GitHub awsm-research/DeepLineDP, not the paper), the dataset comes from Wattanakriengkrai et al. and includes ActiveMQ with 5 releases (R1-R5).
- **Representation**: Per abstract: tokens and lines of source code ('surrounding tokens and surrounding lines'). The README lists word2vec models per project. No AST/graph.
- **Model**: Per abstract: a deep learning model learning semantic properties of surrounding tokens and lines. Secondary sources (not read in full) describe a hierarchical attention network with Bi-GRU token and line encoders; line scores come from token attention.
- **Baselines**: Per abstract: 'other file-level defect prediction approaches' and 'other line-level defect prediction approaches' (not named in the abstract).
- **Evaluation setup**: Per the README, not the paper: for each project, the oldest release trains, the next release is validation, and the remaining releases are tests (e.g. ActiveMQ R1 train, R2 validation, R3-R5 test). This is a forward-in-time cross-release split with a separate validation release. The abstract also mentions cross-project transfer.
- **Duplication or leakage handling**: Unknown from the abstract (full text not read).
- **Metrics and key results**: Per the DOI-registered abstract: 17%-37% more accurate than other file-level approaches; 47%-250% more cost-effective than other line-level approaches; 'reasonable performance' when transferred to other projects. The Monash repository abstract gives different ranges (14%-24% and 50%-250%), a discrepancy between versions that I cannot resolve without the full text. No absolute numbers are available.
- **Stated limitations**: Unknown (full text not read).
- **Critical assessment**: Could not be assessed in full; the paper is paywalled and no open copy was reachable (ResearchGate full text not accessible; Monash repository record has no PDF). Its replication package is public (GitHub), which is better than most papers in this group, and the README's train/validation/test-by-release protocol is a sound template. A later Bugsplorer paper (arXiv 2312.11889; search snippet only) reports DeepLineDP AUROC of about 0.51 on a cross-release split, suggesting weak absolute performance. Treat that as provisional.
- **Relevance to project**: High practical relevance: its dataset (from Wattanakriengkrai et al.) includes 5 ActiveMQ releases. If the project's 5 ActiveMQ versions are the same releases, DeepLineDP/LineDP results provide a directly comparable published baseline and protocol (oldest train, next validation, later test). Overlap must be verified. Its token-level DL contrasts with the project's CFG+DDG graphs. Read the full text before citing numbers.

## Theme synthesis

Collectively, these papers show how 'semantic' deep-learning defect prediction for code became established on a small and fragile evidence base. Wang et al. (ICSE'16) set the template: AST-token sequences, PROMISE Java projects, an older->newer consecutive-version split labelled 'within-project', and F1 against 20 PROMISE metrics on ADTree/NB/LR. Later work reuses this template almost unchanged: DP-CNN (QRS'17) on 7 of the pairs, Dam et al.'s Tree-LSTM (arXiv'18/MSR'19) on all 16 pairs, and Pan et al.'s CodeBERT study (2021) on the same 7 pairs as DP-CNN. Within that template, headline averages rose from about 0.50 F1 (metrics) to about 0.56-0.64 (DBN, CNN, CodeBERT). Every comparison rests on 7-16 test versions of 150-1,000 files, with no variance, no statistical tests, and baselines that are either weak (a single LR/ADTree on PROMISE metrics, a RANDOM classifier) or taken from another paper's reported numbers.

The papers agree on direction (learned features beat PROMISE metrics in F1) but disagree on magnitude, and the numbers do not reproduce across papers. DP-CNN's re-implemented DBN gives values for identical version pairs that differ from Wang et al.'s (e.g. lucene 2.0->2.2: 0.758 vs 65.1 F1; camel 1.4->1.6: 0.335 vs 37.4; different classifier). Dam et al., on real PROMISE labels, obtain only about 0.6 AUC and 17% lower F1 than DBN. Their impressive 0.98 AUC comes from random 10-fold CV on labels produced by a static analyser. Pan et al.'s plain fine-tuned CodeBERT (0.565 average F1) scores below DP-CNN's reported 0.608 on the same 7 version pairs. That is a cross-paper comparison with different file counts, so it is indicative only, but it gives no support to the claim that pre-trained models clearly improve file-level cross-version SDP. CodeBERT's reported advantage over training from scratch is small (+0.021 F1 cross-version, +0.009 cross-project). The 'prompt' variants' further gain coincides with lexical cues ('error', 'patch') being enriched in buggy files, which suggests shortcut learning rather than semantics.

Methodological weaknesses are shared and serious. Hyperparameters were chosen on evaluation pairs in Wang'16 (Sec 4.4) and DP-CNN (Sec IV-F). Pan'21 tunes and early-stops on the test set and reports the best F1 of several runs (Sec 4.6, 5.1). F1 at a fixed threshold is the main or only metric in Wang, DP-CNN and Pan (MCC/AUC relegated to supplements); the Giray SLR confirms this field-wide (F1 in 68% of 102 studies, MCC in 20, effort-aware measures in 13). Resampling is applied to training data only where stated (Wang: SMOTE; DP-CNN: duplication; Pan: random oversampling), so test-set resampling is not an issue in these papers. Wang's CLNI noise removal may, however, touch test labels; the paper does not say. None of the papers mentions duplicate or unchanged files between consecutive versions, even though the split puts largely identical code in train and test. That is the most likely unexamined inflation mechanism and exactly what the project's leakage analysis targets. Reproducibility is poor: DBN and TCA+ had to be re-implemented, and Giray et al. find full replication packages in only 11% of studies.

The two surveys add context but not validity checks. Giray et al. (102 studies to 2021) report that DL gains over traditional ML are 'not significant' (qualitative). Only 10 studies are cross-version, CFG/PDG/DFG representations are rare, every commonly used dataset is Java/C/C++, and leakage and transformers are not covered. Li et al. (2024) is a position paper recommending multi-representation fusion (AST + CFG/DFG/PDG + metrics), MCC/AUC plus effort-aware measures (PofB@20%, IFA), and line-level granularity. It mentions duplicate removal only as generic data cleaning and is silent on leakage and pre-trained models. Two potentially central papers could not be read in full: DH-CNN (TR 2024), which fuses AST-Word2vec with CFG+DDG-Node2vec features, and DeepLineDP (TSE 2022), whose public dataset includes 5 ActiveMQ releases with an oldest-train/next-validation/rest-test protocol. Their claims here rest on abstracts only.

Open gaps relevant to the project: (1) no study controls for duplicate or unchanged code across versions, or reports results on changed-only or de-duplicated test sets; (2) no study compares CFG/DDG graph models head-to-head with CodeBERT and metric baselines under the same leakage-controlled cross-version protocol, with DH-CNN (unread) the closest; (3) no Python data appears anywhere in this group; (4) protocol hygiene is missing: a separate validation release for early stopping and tuning, threshold-independent metrics plus MCC and effort-aware measures, multiple seeds with variance, and statistical tests; (5) CodeBERT's input truncation and possible pre-training contamination (Apache Java in CodeSearchNet) are never addressed, and function-level units like the project's per-function graphs largely remove the truncation issue.
