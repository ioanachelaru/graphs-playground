# GNN on intra-procedural program graphs for defect prediction — reading notes

Full text read: 10.1109/ictai.2017.00019 (arXiv preprint), 10.1109/access.2022.3144598. Abstract/secondary only: 10.1109/tr.2020.3040191, 10.1109/tr.2022.3161581, 10.1109/access.2022.3213844. Not found (no abstract): 10.1016/j.infsof.2022.107057. Every claim about the non-full-text papers is provisional.


## Phan, Nguyen & Bui, 2017, Convolutional Neural Networks over Control Flow Graphs for Software Defect Prediction, ICTAI 2017 (arXiv:1802.04986)

DOI: 10.1109/ictai.2017.00019 — access: **full_text**

- **Task & granularity:** Multi-class (5-class) classification of whole programs (single-file competitive-programming submissions) by judge outcome: accepted, time limit exceeded, wrong answer, runtime error, syntax error (Sec. III-A). Granularity = one program/file. This is not module-level defect prediction from version history.
- **Language & data:** C/C++ submissions to four CodeChef problems collected up to 14 Mar 2017 (Sec. III-A): FLOW016 10,648; MNMX 8,745; SUBINC 6,484; SUMTRIAN 21,187 instances (Table I). Strongly imbalanced, e.g., MNMX class 0 = 5,157 and class 2 = 189 (Table I). Empty and non-compiling files were removed. Note that the 'syntax error' class (class 4) is still listed with 213-1,987 instances even though non-compilable files were said to be removed; the paper does not explain this inconsistency.
- **Representation (graph construction):** CFG over ASSEMBLY instructions, not source. The source is compiled with g++ on Linux to assembly, and a custom algorithm (Algorithm 1, Sec. II-A) partitions the code into label-delimited blocks. Each NODE = one assembly instruction, so the graph is at instruction level, not basic-block level, even though the text defines basic blocks. EDGES: sequential next-instruction edges, jump edges to the first instruction of the target block, and two edges per call (call -> callee first instruction, callee last instruction -> instruction after the call). All edges are untyped directed edges, and the graph covers the whole program, i.e., it is inter-procedural across the file. NODE FEATURES (Sec. III-B): two 'views', (1) the instruction with operands abstracted to the symbols name/reg/val (e.g., 'addq $32,%rsp' -> 'addq value, reg') and (2) the instruction type group (e.g., jne/jle/jge -> conditional jump). Each view vector is the mean of randomly initialised, learned symbol embeddings (Eq. 2). There is no aggregation step because the label is per file.
- **Model:** DGCNN (multi-view multi-layer directed graph-based CNN). Two graph-conv layers (GC100-GC600) use separate weight matrices for the current, incoming and outgoing neighbours (Sec. II-B), followed by one-way dynamic max pooling to a fixed vector, then FC600 and a 5-way softmax (Table II). Activation is tanh and the initial learning rate is 0.1.
- **Baselines:** AST-based models from pycparser ASTs: TBCNN, SibStCNN, and RvNN (recursive NN). Also kNN (k=3) with tree edit distance and with Levenshtein distance, and an RBF SVM on AST bag-of-words (C=1, gamma=0) (Sec. III-B). No software-metric baseline was evaluated, although Sec. I argues that RSM metrics cannot separate the motivating example. No pretrained model was used.
- **Evaluation setup:** Random 3:1:1 train/validation/test split per dataset (Sec. III-A), done once. No cross-validation and no repeated runs. No resampling. Labels are online-judge verdicts, not bug-fix mining. There is no versions concept, so there is no cross-version or cross-project setting.
- **Duplicates / leakage:** Not discussed. Competitive-programming submissions commonly include near-identical resubmissions by the same user and copied solutions. A random split therefore very likely places near-duplicates in both train and test, and the paper does nothing to control this.
- **Metrics & key results:** Accuracy (Table III) and macro-averaged AUC (Table IV). Best DGCNN accuracies: FLOW016 75.49 (1V Op), MNMX 84.05 (1V Op), SUBINC 76.02 (2V Op), SUMTRIAN 68.95 (2V Op). Strongest baselines: FLOW016 TBCNN 63.10, MNMX SibStCNN 82.85, SUBINC TED 68.31, SUMTRIAN TED 66.97 (Table III). Reported gains over the second-best are +12.39 (FLOW016), +1.2 (MNMX), +7.71 (SUBINC) and +1.98 (SUMTRIAN) points (Sec. IV). AUC: DGCNN 0.74-0.82 vs. the best tree baseline 0.71-0.80 (Table IV), an average improvement of 0.03 (Sec. IV). Minority-class AUC is weak, e.g., class 2 AUC 0.59 for DGCNN 1V NoOp on MNMX (Fig. 4b).
- **Stated limitations:** Error analysis (Sec. V): CFGs are sensitive to semantically equivalent statement replacements (int vs. long, printf vs. cout), which change the instructions. Library procedures (e.g., __gcd) are not inlined, so their semantics are invisible to both the CFG and the AST.
- **Critical assessment:** This is a program-correctness classification task, not software defect prediction in the PROMISE/version-history sense. The labels include 'syntax error' and 'time limit exceeded', and the programs are small single-file solutions to 4 problems. The evidence comes from a single random split with no variance or significance testing and only accuracy and AUC. Near-duplicate leakage is likely and unaddressed. Baselines are AST-only, with no metrics or token models. The approach requires compilation, which does not transfer to Python. On the positive side, code and datasets are released (github.com/nguyenlab/DGCNN, footnote 3). The gains are modest on 2 of the 4 datasets (+1.2 and +1.98 points accuracy).
- **Relevance to project:** Low-to-moderate. It is the seminal CFG+GNN 'defect' paper that later DP papers cite, but its CFG is built from compiled assembly, so it is not applicable to Django (Python), and it is only partially applicable to ActiveMQ (bytecode would be the analogue). Its multi-view node encoding (instruction + instruction type) is the analogue of Joern node text + node kind ('kind' field) and supports encoding both. The use of separate weights for incoming vs. outgoing edges supports keeping edge direction and type (CFG vs. DDG) as relational edges, e.g., R-GCN/edge-typed GGNN. The paper provides no cross-version or leakage evidence.

## Xu, Wang & Ai, 2021 (online 2020), Defect Prediction With Semantics and Context Features of Codes Based on Graph Representation Learning, IEEE Transactions on Reliability 70(2):613-625

DOI: 10.1109/tr.2020.3040191 — access: **abstract_only**

- **Task & granularity:** Per the abstract, it identifies defect patterns from AST subtrees, with 'defective subtrees ... pruned based on a fix-inducing change'. The exact prediction unit is not verifiable from the abstract. A secondary description (Šikić et al. 2022, Sec. II and V-B) says it uses only part of the AST of code snippets, plus project information and fix-inducing changes.
- **Language & data:** Abstract: '6052 defects from 307 projects', mined with rules based on the GitHub workflow. Language is per a secondary source only: Šikić et al. 2022 Sec. V-B describes 'modules from various Java projects'. Instance counts, non-defect counts and defect ratio were not available.
- **Representation (graph construction):** Abstract: AST representation learning combining semantics and 'context' (code concepts). Per the abstract, defective subtrees are pruned based on the fix-inducing change. Secondary sources: Šikić et al. Sec. V-B says AST nodes are 'enriched with the concept features'. A 2021 survey snippet says buggy and fixed ASTs are pruned using a community-detection algorithm. The parser/tool, node feature encoding, edge types and file-level aggregation could not be verified.
- **Model:** Graph neural network (end-to-end GCNN per Šikić et al. Sec. V-B). The architecture details were not available.
- **Baselines:** Abstract: 'the state-of-the-art approach and five traditional machine learning baselines'. Their identities were not available.
- **Evaluation setup:** Not available (abstract only). Split type, cross-validation and resampling are unknown.
- **Duplicates / leakage:** Unknown (abstract only). Pruning based on fix-inducing changes uses information from the fix, i.e., future knowledge. If the same pruning is applied to test instances, it may leak the label. This must be checked in the full text.
- **Metrics & key results:** Abstract only: the approach 'performs better than the state-of-the-art approach and five traditional machine learning baselines'. An ablation shows code-concept information gives a 'significant increase in accuracy'. No numbers were available.
- **Stated limitations:** Not available (abstract only).
- **Critical assessment:** Cannot be assessed in depth without the full text. Red flags from the abstract: (1) defective subtrees selected using the fix-inducing change may not be reproducible at prediction time, which is a potential label leakage. (2) 307 GitHub projects with a novel mining rule set make the results incomparable with PROMISE-style benchmarks. (3) Accuracy is emphasised in the abstract. Code/data release is unknown.
- **Relevance to project:** Moderate in concept, unverified in detail. Its pruning of the graph to fix-related regions is a design choice that the Joern per-function setup avoids, because whole function graphs are labelled. If the project ever restricts graphs to changed regions, this paper's approach is the leakage risk to avoid. The full text is needed before citing any specifics.

## Šikić, Kurdija, Vladimir & Šilić, 2022, Graph Neural Network for Source Code Defect Prediction, IEEE Access 10:10402-10415

DOI: 10.1109/access.2022.3144598 — access: **full_text**

- **Task & granularity:** Binary file-level (Java class/file) defect prediction, cross-version within-project (Sec. II-A, IV-A).
- **Language & data:** Java, seven Apache PROMISE projects with two consecutive versions each (Table 2): camel 1.4->1.6 (872/965 files, 16.63%/19.48% defective); jedit 4.0->4.1 (306/312, 22.60/25.32%); lucene 2.0->2.2 (195/247, 46.67/58.30%); poi 2.5->3.0 (385/442, 64.42/63.57%); synapse 1.1->1.2 (222/256, 27.03/33.59%); xalan 2.5->2.6 (803/885, 48.19/46.44%); xerces 1.2->1.3 (440/453, 16.14/15.23%). The '#Nodes' column (77-260) appears to be the average AST nodes per file. Source code was re-downloaded from project repositories and matched to PROMISE labels (Sec. IV-A).
- **Representation (graph construction):** AST only, no CFG or data flow. Tool: the Python 'javalang' parser (Sec. III-A). Only 39 javalang node types are kept (Table 1: declarations, statements such as If/While/For/Try/Switch/Return/Throw, invocations, member references, creators, etc.). Selecting nodes can fragment the tree, so a synthetic root node is added and linked to each fragment's root. NODE FEATURES: a 40-dim one-hot node-type vector (39 types + root). There are no identifiers, literals or token text. EDGES: undirected AST parent-child adjacency of a single type. GRANULARITY: one whole-file AST per instance, so no aggregation is needed. All ASTs are zero-padded to the size of the largest AST in the project (Sec. III-B).
- **Model:** DP-GCNN: a spectral GCN with Chebyshev filters of order K=3 (Defferrard et al.), three conv + MinCutPool levels with dropout, global average pooling, a dense layer and a sigmoid output. Layer widths scale with the project's maximum AST size (Sec. III-B, IV-C). Loss is class-weighted binary cross-entropy. Training uses Adam for 200 epochs with early stopping (patience 20) on a random 10% of the training set (Sec. IV). Batch size is 4 for tuning. Dropout is 0.3 (0.5 for camel), and the learning rate was tuned per project.
- **Baselines:** RQ1 (run by the authors): logistic regression (LRC) and random forest (RFC) on the 20 PROMISE static code metrics, tuned by random search with 10-fold CV on the training version and class-weighted. RQ2: published numbers only, NOT re-run — DBN (Wang et al.), CNN (Pan et al. 2019), SEML (LSTM), MPT-embedding, DP-T (Transformer), and CSEM (GNN on AST+CFG, Zhao et al. 2022; xalan missing) (Sec. IV-D).
- **Evaluation setup:** Cross-version within-project: train on all files of the older version, test on all files of the newer version (Sec. IV-A). Hyperparameters were tuned with 10-fold CV on the older version of camel, lucene and xalan only (Sec. IV-C). However, the learning rate in RQ2 was set per project 'so that the learning process converges' (Sec. IV-E2), and the selection criterion relative to the test version is unclear. The training was repeated 30 times, but the train/test split is fixed (only the seed varies). Class weights are used, with no resampling of the test set. Labels come from PROMISE (Jureczko & Madeyski). Statistics: Friedman test with Holm post-hoc over 7 projects (Tables 5-6).
- **Duplicates / leakage:** Not discussed. Consecutive versions such as camel 1.4/1.6 and xerces 1.2/1.3 share many unchanged files. Because node features are type-only one-hot vectors, unchanged files produce identical graphs, so the model can memorise per-file labels that carry over between versions. The paper neither measures nor controls this. Known PROMISE label noise and source-matching issues are also not discussed.
- **Metrics & key results:** AUC and F1 (Table 3, mean ± sd over 30 runs). DP-GCNN AUC / F1 per project: camel 0.62/0.39, jedit 0.76/0.64, lucene 0.63/0.77, poi 0.74/0.83, synapse 0.67/0.59, xalan 0.71/0.72, xerces 0.63/0.35. Mean AUC: DP-GCNN 0.68 vs. LRC 0.63 vs. RFC 0.61. Mean F1: 0.61 vs. 0.51 vs. 0.48 (Table 4). Friedman p = 0.008415 (AUC) and 0.003725 (F1). Holm p for AUC: vs. LRC 0.0161569, vs. RFC 0.0050123 (Table 6). Against the published DL numbers (Fig. 6), mean F1 excluding xalan: DP-GCNN 0.595 vs. MPT 0.614, DP-T 0.608, CNN 0.591, CSEM 0.568, DBN 0.568, SEML 0.565 (Sec. IV-E2). The authors call these 'comparable', i.e., DP-GCNN is not better than the AST-token DL baselines. The baseline RFC AUC for xerces is 0.50 ± 0.00, i.e., chance level (Table 3), which suggests a poorly configured metric baseline.
- **Stated limitations:** Sec. VI: external validity is limited to the PROMISE projects. The choice of baseline models may bias internal validity. Other metrics are possible. Comparison with the state of the art is only 'indicative' because those studies used fewer than 30 repetitions and their numbers were copied from the papers. Future work: other module sizes and other languages (Sec. VII).
- **Critical assessment:** (1) The metric baselines appear weak: RFC AUC 0.50-0.68 with zero variance across 30 runs, which is odd for a random forest. Mean AUC of 0.61-0.63 is below what tuned RF/LR typically achieve on these PROMISE pairs. (2) The headline comparison with the state of the art uses copied F1 numbers from papers with different preprocessing and different selection of PROMISE files, so it is not a controlled comparison. (3) F1 is threshold-dependent and highly sensitive to the defect ratio, e.g., poi at 64% defective. No MCC or effort-aware metrics are reported. (4) Per-project learning-rate selection 'so that training converges' risks implicit test tuning. (5) Only one version pair per project and seven pairs in total, so n=7 for the Friedman test. (6) Duplicates and unchanged files across versions are not considered. (7) Node features are type-only, discarding identifiers and literals. On the positive side, code is released (gitlab.com/LSikic/dp-gcnn), variance across 30 runs is reported, and the statistical tests are proper.
- **Relevance to project:** High as a design reference and a cautionary example. (a) It is the clearest cross-version file-level GNN setup to replicate, and the 'train on version N, test on N+1' protocol matches the project's CVDP. (b) It shows that a type-only one-hot node encoding plus a whole-file AST graph gives AUC around 0.68. For the project's Joern graphs, the analogous feature set is a node-'kind' one-hot, and adding CFG+DDG edges and node text embeddings would be the obvious ablations. (c) Unchanged files produce identical graphs under this encoding, so this paper is a concrete example of where the project's duplicate/unchanged-code leakage analysis applies. It is worth re-running DP-GCNN-style models on de-duplicated test sets. (d) Its weak metric baselines highlight the need for properly tuned SonarQube-metric RF/LR baselines. (e) There is no Python and no CFG/DDG, and padding to the maximum AST size will not scale to Django files. Per-function graphs with pooling to the file level (as in the project) are a necessary departure.

## Gupta, Rajnish & Bhattacharjee, 2022, Cognitive Complexity and Graph Convolutional Approach Over Control Flow Graph for Software Defect Prediction, IEEE Access 10:108870-108894

DOI: 10.1109/access.2022.3213844 — access: **abstract_only**

- **Task & granularity:** Abstract: binary defect/no-defect classification of whole small programs. The programs were also grouped into Simple/Medium/Complex classes.
- **Language & data:** Abstract: Python. The dataset is 320 Python programs written by undergraduate and postgraduate students during lab classes. Labels were set by the students together with three lab programmers who compiled/ran each program and detected defective vs. non-defective ones. The defect ratio was not available. Although the paper is gold OA, the PDF could not be retrieved here.
- **Representation (graph construction):** Abstract: a CFG per program. CFG nodes are categorised by node features, with 'seven unique features' each assigned an integer value evaluated through Cognitive Complexity Measures (Wang's cognitive weights of basic control structures). These values are the node features. A node-vector matrix is then built and passed to a GCN. The CFG construction tool, edge types and granularity are not available from the abstract.
- **Model:** Abstract: GCN for graph features, whose output forms datasets for downstream DNN-DP and CNN-DP classifiers. Implemented in Keras/TensorFlow.
- **Baselines:** Abstract: Naive Bayes, Decision Tree, SVM and Random Forest. Their input features are not specified in the abstract.
- **Evaluation setup:** Not available. The abstract mentions hyper-parameter tuning, accuracy, ROC/AUC, F-measure and precision. The split type is unknown. There are no versions, so cross-version evaluation does not apply.
- **Duplicates / leakage:** Unknown (abstract only). Student lab programs for shared exercises are likely to be near-duplicates, which is a probable risk under random splits.
- **Metrics & key results:** Abstract only: proposed models 'outperformed' NB, DT, SVM and RF 'in all evaluation criteria'. No numbers available.
- **Stated limitations:** Not available.
- **Critical assessment:** This is a tiny (320 programs), artificial, lab-generated dataset with labels from manual execution, not from real defect history. Its baselines are classical classifiers rather than strong code models. If the paper is used at all, it should only support the claim that CFG+GCN has been tried on Python. It is the only Python CFG defect-prediction study in this group, but on toy data.
- **Relevance to project:** Low for evidence, moderate as the sole Python precedent. It shows that Python CFG+GCN for defect prediction exists only at toy scale, which strengthens the novelty claim for Joern CFG+DDG on real Django releases with cross-version evaluation. Its cognitive-weight node features (control-structure type weights) are a cheap hand-crafted node feature that could serve as an ablation against Joern node-kind one-hot encodings.

## Synthesis

Only two of the six assigned papers could be read in full (Phan et al. 2017; Šikić et al. 2022). The other four are closed-access or failed to download (Xu et al. 2020, ACGDP 2022, Zhou et al. 2022, Gupta et al. 2022), and statements about them rest on abstracts or secondary citations. Every claim about those four is provisional.

How graphs are built. The group spans four representation families, and none matches the project's Joern per-function CFG+DDG setup. (1) Phan et al. compile C/C++ with g++ and build an instruction-level CFG over assembly, using sequential, jump and call/return edges, untyped and inter-procedural within the file. Node features are averaged embeddings of the opcode and abstracted operands (name/reg/val) plus an instruction-type 'view'. (2) Šikić et al. parse Java with javalang and keep 39 AST node types. Each node is a 40-dim one-hot type vector with undirected parent-child edges, and there is one graph per file, zero-padded to the project's largest AST. Neither paper needs file-level aggregation, because each graph is already the whole file. (3) Xu et al. 2020 (abstract) use AST subtrees pruned by fix-inducing changes with 'concept' features. ACGDP (abstract) uses an augmented code property graph (AST+CFG+PDG), the representation closest to Joern output, but its construction details are unknown. (4) Gupta et al. (abstract) use Python CFGs whose node features are integer cognitive-complexity weights of control structures. Zhou et al. appear to use a class dependency network rather than an intra-procedural graph. No paper in the group combines per-function CFG and data-dependence graphs pooled to file level, and none states its edge typing in a way that separates control-flow from data-dependence edges in the GNN.

What the evidence shows. The only properly cross-version study (Šikić et al.: train on version N, test on N+1, 7 PROMISE pairs) found that an AST-type GCN beats LR and RF on PROMISE static metrics: mean AUC 0.68 vs. 0.63/0.61 and mean F1 0.61 vs. 0.51/0.48 (Table 4). It is only 'comparable' to AST-token DL models, with mean F1 0.595 vs. MPT 0.614 and DP-T 0.608 (Sec. IV-E2). The metric baselines look under-configured (RFC AUC 0.50 ± 0.00 on xerces, Table 3). The state-of-the-art comparison is copied from papers, not re-run. Phan et al. report gains of +1.2 to +12.4 accuracy points over AST models (Table III), but on a single random split of competitive-programming submissions with judge-verdict labels. That is a program-correctness task, not release-based defect prediction. So the full-text evidence that graph structure beats strong metric or embedding baselines in cross-version defect prediction is weak: one study, n=7 version pairs, weak baselines and F1-centric reporting.

What is missing. Neither full-text paper mentions duplicates, unchanged files across versions, or train/test leakage. Both setups are exposed to it. Random splits of judge submissions almost certainly contain near-duplicate resubmissions. Under Šikić's type-only one-hot encoding, an unchanged file has an identical graph in both versions, so its label can be memorised. Two of the abstract-only papers (Xu 2020, ACGDP) select graph regions using fix or defect-category information, which is a potential label-leakage path that must be checked in their full texts. None reports MCC or effort-aware measures. None compares against pretrained code models (CodeBERT/GraphCodeBERT) or doc2vec. Only Phan et al. and Šikić et al. release code.

Gaps for this project. (a) Python is represented only by a 320-program student dataset (Gupta, abstract). Joern CFG+DDG on real Django releases would therefore be new. (b) No study compares CFG-only vs. DDG-only vs. CFG+DDG with typed edges. (c) No study aggregates per-function graphs to file labels, which the project needs and should report explicitly (e.g., mean/max pooling vs. attention over function embeddings, and how files with no functions are handled). (d) No study evaluates on de-duplicated or changed-only test sets. The leakage analysis is therefore a clear contribution: re-scoring a DP-GCNN-style baseline on new/changed files only would test whether reported cross-version gains survive. (e) Strong, tuned metric baselines (SonarQube metrics with RF/LR) and embedding baselines (doc2vec, CodeBERT) under the same split, with MCC and effort-aware metrics, are absent from this literature and should be part of the comparison.
