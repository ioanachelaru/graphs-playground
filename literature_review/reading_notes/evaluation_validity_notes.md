# Evaluation validity — duplication, label quality, realistic splits, strong baselines, statement-level graph models

Per-paper notes from full-text reading (8 papers) and abstract only (Liu et al. 2024, paywalled; Wiley blocked automated download and no preprint was found). All numbers carry their table/section location in the source.

Sources read: arXiv preprints for Allamanis (1812.06469v6), Croft (2301.05456v1), PrimeVul (2403.18624v2), ReVeal (2009.07235v1), IVDetect (2106.10478v1), LineVD (2203.05181v2); the author copy (ORBilu) for Jimenez; the author-site PDF for Zeng. Preprints may differ slightly from the published versions.

## Synthesis

Across the eight papers read in full and one read as abstract only, the main finding is that evaluation choices move headline numbers more than model choices do, often by a factor of two to ten. Label timing: Jimenez et al. (FSE'19) show that the same random-forest vulnerability predictors fall from MCC 0.77/0.65/0.43 to 0.08/0.22/0.10 (Linux/OpenSSL/Wireshark) once training labels are restricted to vulnerabilities known at release time. Cross-set duplication: Allamanis (Onward'19) measures inflation of 5-51% relative on code-ML tasks (Tables 3-4); Croft et al. (ICSE'23) find MCC drops of 0-82% when test-set duplicates are removed (Table V: Devign -13.9%, D2A -81.7%, Big-Vul 0.0%); Ding et al. (PrimeVul, ICSE'25) find 0.6-18.9% exact-copy test leakage in popular benchmarks. Label noise: 20-71% (Croft, n=70 per dataset) and 40-76% (PrimeVul Table I) of vulnerable labels produced by fix-commit heuristics are wrong. Benchmark realism: in combination (clean labels, de-duplication, chronological commit-grouped split, about 1:32 class ratio), StarCoder2 F1 falls from 68.26 to 3.09 (PrimeVul Table V), and ReVeal (TSE'21) reports 54-73% average F1 loss when published models meet realistic data. For the project's setting, Liu et al. (JSEP'24, abstract only) report that unchanged modules across versions significantly change absolute WPDP performance but only slightly change model rankings.

The papers agree on mechanisms. Duplicates come mostly from multiple versions of the same repository ("updated code", Croft; "different versions of the same file", Allamanis; unchanged modules, Liu). Leakage benefits high-capacity and identifier-sensitive models most (Allamanis Fig. 2; LineVD notes identifier names help random splits). Random splits mix past and future (PrimeVul "time travel"). They differ in emphasis and in one substantive point: Allamanis predicts that duplication can reorder models (bigger models memorise more), whereas Liu et al. report ranking stability for WPDP learners. The likely reason is that Liu studied classical learners on metric features. This should be tested for CodeBERT/GNN models; nobody in this set did so. Croft finds no measurable concept drift (currentness test), whereas Zeng et al. (ISSTA'21) and McIntosh-style analyses find that more or older history does not help JIT models. Both use date-sorted splits but different granularities and tasks.

Strong simple baselines: Zeng et al. show that logistic regression on one feature (lines added) beats DeepJIT/CC2Vec (mean within-project AUC 0.7246 vs 0.7065; cross-project 0.7246 vs 0.6808). The released DeepJIT code actually reduced code changes to "added_code/removed_code" placeholders, i.e. a file count, and that version outperformed the semantic one. Within the graph papers, the graph-specific gain is small once other factors are controlled. In ReVeal, removing the GGNN costs about 2 F1 points (41.25 to 39.09), SMOTE is worth about 19 points, and SVM on the same embeddings scores 39.85. In LineVD, function-level gating gives most of the gain (0.129 to 0.296 F1); the GAT over the PDG adds 0.064, and GCN over the same graph is worse than no GNN. IVDetect's incremental ablation (AUC 0.83 to 0.85 to 0.90 when adding control then data dependencies) is the strongest pro-graph evidence, but it was obtained under random, non-de-duplicated splits in a single run. LineVD likewise finds data-dependency edges better than control-only. No paper in the group compares graph models against a software-metrics model (LOC, complexity, churn) under a leakage-controlled split.

Weaknesses in the evidence: the graph models (ReVeal, IVDetect, LineVD) all use random function-level splits on C/C++ datasets that contain pre-/post-fix pairs and unchanged copies, i.e. the very leakage the methodological papers quantify. ReVeal explicitly (and incorrectly) argues that GGNN features make samples unique. F1 dominates reporting; only Jimenez and Croft use MCC, only PrimeVul uses a fixed-FPR operating point (VD-S), and only Jimenez reports effort-style metrics (inspection effort ratio, top-10). Variance is reported by ReVeal (IQR over 30 runs), Allamanis (std, NLM only) and Zeng (RQ1 only). PrimeVul, IVDetect, Croft (5 runs, no spread shown) and LineVD (10 seeds, means only) give no spread. Several papers contain internal numeric inconsistencies (Jimenez 1,898 vs 1,593 vulnerabilities; Croft 17-99% vs Devign about 10% duplication and 65% vs 80% precision drop; IVDetect 43-84% vs 64-122%; LineVD Table 3 rows identical to Table 4 rows). Labels for statement-level models (LineVD, IVDetect) are partly defined via the same PDG dependencies the models consume, which risks circularity. Test-set resampling: LineVD and IVDetect keep the natural ratio in test but balance training. ReVeal balances only training via SMOTE. Jimenez applies SMOTE to training. None was found resampling the test set, which is good practice.

Open gaps directly relevant to this project: (1) no study evaluates CFG/DDG graph models under cross-version splits with unchanged/duplicate functions removed from the target version; (2) none covers Python or mixed Python/Java (only Allamanis' detector tokenises Python and Java); (3) none disentangles the factors (labels as-of release time vs leakage vs class ratio vs drift) in one ablation, although PrimeVul's 68-to-3 F1 drop combines all of them; (4) none checks whether leakage changes the ranking between metric models (e.g. SonarQube), text embeddings (doc2vec/CodeBERT) and graph models, which Allamanis predicts and Liu (abstract) partly contradicts; (5) none uses pair-wise buggy-vs-fixed evaluation on defect (not vulnerability) data. Recommended protocol synthesised from the group: as-of-release labels (Jimenez); hash-based plus near-duplicate de-duplication of functions with whitespace/comment normalisation, removing or separately reporting unchanged target functions (PrimeVul, Croft, Liu, Allamanis); resolve label-conflicting duplicates (Croft); chronological/version splits with commit-grouping (PrimeVul); LOC/size-only and metric baselines plus a kNN memorisation probe (Zeng, Allamanis); a no-message-passing ablation and CFG-only vs CFG+DDG ablation (ReVeal, LineVD, IVDetect); MCC, PR-AUC, FNR@fixed FPR, effort-aware top-k, and paired buggy/fixed evaluation; multiple seeds with spread and significance tests.

## Per-paper notes

### Allamanis, 2019, "The Adverse Effects of Code Duplication in Machine Learning Models of Code", Onward!/SPLASH 2019 (read as arXiv 1812.06469v6)
DOI: 10.1145/3359591.3359735

- **Access:** full_text
- **Task & granularity:** Methodological study of near-duplicate code in ML-for-code corpora; tasks: token-level language modelling/autocompletion, method naming, variable naming, docstring generation. Duplication measured at file level (method level for corpora split per method). No defect prediction task.
- **Language & data:** 10 public corpora (Table 1): C#-19, Concode-Java, Java GitHub Corpus, Java-Small, Java-Large, JavaScript-150k, Python-150k, Python docstrings v1/v2, Python Autocomplete. Files with <20 identifier/literal tokens excluded. Duplicate-file share d: 4.7% (Java-Small) to 68.7% (Concode, method-level); Python-150k 6.6%, Python docstrings v2 31.5% (Table 1).
- **Representation:** Near-duplicate detector re-implementing SourcererCC at file level: identifier+literal token set T0 and multiset T1; pair is duplicate if Jaccard(T0)>=0.8 and Jaccard(T1)>=0.7; transitivity assumed (Sec. 3). Tokenizers for Java, JS, C#, Python. Precision checked on 100+100 random pairs by the author: no false positives reported (Sec. 3).
- **Model:** Bengio-style feed-forward neural LM (D=128, 10k vocab); code2vec; JsNice; PHOG; Seq2Seq docstring model (outputs supplied by original authors).
- **Baselines:** Not a model-proposal paper; compares each model under biased vs. de-duplicated evaluation. Recommends adding naive memorisation baselines (e.g. kNN) as a duplication sanity check (Sec. 5).
- **Evaluation setup:** Random 50-10-40 train/validation/test split over files (Sec. 4); datasets re-shuffled from original splits. Four evaluation regimes (Table 2): fully unbiased, unbiased test, cross-set biased, fully biased. Correct effect estimate = cross-set biased vs. unbiased test with the same trained model. NLM results averaged over 5 random splits with std (Table 3); other models single run.
- **Duplication / leakage:** Central topic. Defines in-train, in-test and cross-set duplicates and decomposes metric bias as f_hat=(1-d)f_bar+d*beta (Eq. 2). Expected cross-set duplicates in test under a 6:4 random split: 5.7%-77.8% (Table 1); for Java-Large, project-wise split reduces cross-set duplicates from 24.1% to 8.9%. Higher-capacity models are more inflated (Fig. 2). Training on duplicated data usually also lowers de-duplicated test performance (Sec. 4.3). Notes that temporal (train-older/test-newer) splits are valid but still need de-duplication (Sec. 5).
- **Metrics & key results:** Table 3 (NLM, JavaScript-150k, mean±std over 5 runs; unbiased test vs. cross-set biased): Acc 49.1 vs 55.1 (-10.9%); identifier accuracy 8.6 vs 17.7 (-51.4%); MRR-ID 0.136 vs 0.224 (-39.3%); PPL 9.4 vs 7.5 (+25.3%). Table 4: code2vec F1 44.71 vs 50.98 (-12.3%); JsNice accuracy 34.44 vs 55.04 (-37.4%); PHOG string-literal accuracy 25.62 vs 43.89 (-41.6%); docstring BLEU 12.32 vs 13.86 (-11.1%). Abstract: metrics inflated "by up to 100%".
- **Stated limitations:** Only file-level duplicates; small-snippet clones and semantic (type-IV) clones are not counted (Sec. 2). The study is not exhaustive (Sec. 4). The duplicate detector assumes transitivity. Some tasks (JsNice deobfuscation) legitimately include duplicates in the target distribution.
- **Critical assessment:** Strong, simple and widely cited argument with an open tool (github.com/Microsoft/near-duplicate-code-detector, dpu-utils) and a released duplicate index. Weaknesses: no classification task with label noise or class imbalance, so the effect size on defect or vulnerability prediction is not measured; most Table 4 results are single runs; the precision check was done by the author alone and recall of the detector was not measured. The method-level corpora (Concode, docstrings) have the highest duplication, which suggests that per-function datasets such as this project's are the most exposed.
- **Relevance to project:** Directly applicable. Per-function Django/ActiveMQ graphs across 22/5 versions share many unchanged or near-identical functions, which are cross-set duplicates under any version split. Recommended practice: report unbiased-test metrics (remove test functions whose normalised token or AST hash matches a training function), keep exactly one copy per near-duplicate cluster or down-weight duplicates by 1/c_i (Eq. 4), and add a kNN/memorisation baseline. High-capacity models (CodeBERT, GNNs) are expected to gain more from leakage than SonarQube-metric models, so leakage can reverse model rankings. The available tokenizers cover both Python and Java.

### Liu, Zhou, Lu, Mei, Yang, Qian, Zhou, 2024, "Unveiling the impact of unchanged modules across versions on the evaluation of within-project defect prediction models", Journal of Software: Evolution and Process 36(12):e2715
DOI: 10.1002/smr.2715

- **Access:** abstract_only
- **Task & granularity:** Within-project (cross-version) defect prediction evaluation; module level (granularity beyond "modules" not stated in the abstract).
- **Language & data:** 481 target versions from 62 projects (abstract). Languages, dataset sources, defect ratios: not available from the abstract.
- **Representation:** Not available from the abstract. A method to detect unchanged modules, i.e. "identical executable source code" between source and target versions, is proposed.
- **Model:** Not available from the abstract (multiple WPDP learners are compared).
- **Baselines:** Not available from the abstract.
- **Evaluation setup:** Cross-version WPDP: train on labelled modules of previous versions and test on a target version; performance compared with and without unchanged modules removed from target versions (abstract).
- **Duplication / leakage:** Central topic: unchanged modules (identical executable code in source and target versions) are frequently present in both, constituting data duplication. The authors provide a detection/removal method and recommend removing unchanged modules from target versions when evaluating WPDP models (abstract).
- **Metrics & key results:** Abstract only: removing unchanged modules "significantly affects the reported performance values of individual learners"; the effect on rankings of multiple models is "not substantial", with a "slight influence" on selecting better-generalising models. Exact magnitudes, metrics and tables: not available (full text not accessed).
- **Stated limitations:** Not available (full text not accessed).
- **Critical assessment:** Cannot be assessed beyond the abstract. Notable claim: duplication changes absolute performance but not model rankings much, which contrasts with Allamanis' finding that high-capacity models benefit more from duplication. However, those were probably classical learners on metric features, so the ranking stability may not transfer to CodeBERT/GNN models. Direction and size of the effect (whether removal raises or lowers performance) are not stated in the abstract. All numbers are provisional until the full text is read.
- **Relevance to project:** Very high and direct: same setting (cross-version WPDP) and same issue (unchanged modules across versions). For Django's 22 versions and ActiveMQ's 5, unchanged functions between consecutive versions will be common. Recommended practice from the abstract: identify unchanged modules (identical executable code, i.e. ignoring comments/whitespace) and remove them from target versions, or report results on the changed subset. The project can extend this to function level and to representation-learning models, where the ranking may change more than for metric-based learners.

### Jimenez, Rwemalika, Papadakis, Sarro, Le Traon, Harman, 2019, "The Importance of Accounting for Real-World Labelling When Predicting Software Vulnerabilities", ESEC/FSE 2019 (read as author copy from ORBilu)
DOI: 10.1145/3338906.3338941

- **Access:** full_text
- **Task & granularity:** Release-based vulnerability prediction at file (component) level (Sec. 2.2).
- **Language & data:** C systems: Linux Kernel (64 releases 2.6.12-4.15), OpenSSL (10 major releases), Wireshark (9 major releases) (Fig. 1). Table 2: 1,593 vulnerabilities and 1,898 vulnerable components (1,202/1,508 Linux; 265/221 Wireshark; 126/164 OpenSSL). Note: the abstract says "1,898 vulnerabilities in 74 releases", which conflates the two counts; 74 is the number of evaluated releases (61+6+7, Sec. 6.1). Vulnerable ratio 1-7% per release (Sec. 5.2). Labels from NVD via VulData7: a file is vulnerable if it was modified by a fix commit.
- **Representation:** Three feature sets (Sec. 2.3): imports and function calls (Neuhaus; AST traversal, minimum support 5%), code + churn + developer metrics (Shin), bag of words (Scandariato, discretised). No graphs.
- **Model:** WEKA 3.9.2 with default hyperparameters: AdaBoost, J48, KNN(k=5), logistic regression, random forest. Random forest + SMOTE + last three releases selected in a pre-analysis (Sec. 6.3).
- **Baselines:** The three literature approaches compared with each other; no trivial baseline (e.g. LOC-only or a random ranker).
- **Evaluation setup:** Release-based, chronological: train on previous 1 or 3 releases, test on the next; start from the 4th release; only releases with >=10 vulnerable components (Sec. 6.1). Two labelling regimes: "realistic", where training labels contain only vulnerabilities reported before the release date, and "ideal/perfect", where all labels known at any time are used. The test set is always evaluated against full ground truth. SMOTE applied (training side). RQ3 augments training with bug-fixed files at weight 1 vs 5 for vulnerable files.
- **Duplication / leakage:** Addresses temporal label leakage: future-discovered vulnerabilities used as training labels. Table 1 shows that all prior studies used cross-validation, which "does not consider the temporal aspect". Code duplication across releases is not discussed, although consecutive releases share most files.
- **Metrics & key results:** MCC mean, ideal vs realistic labels (abstract, Sec. 1, Sec. 8): Linux 0.77 to 0.08, OpenSSL 0.65 to 0.22, Wireshark 0.43 to 0.10. Table 1: ideal-world precision 44.7-83.3 and recall 33.5-76.5; real-world precision 19.4-44.6 and recall 1.6-26.2. RQ1 (Sec. 7.1): precision <0.4 and recall <0.2 on average; top-10 contains 2-5 vulnerable files, and the effort ratio requires inspecting "almost the whole codebase" (Fig. 5a). Ideal world: 7-10 of top-10 for OpenSSL/Linux. RQ3 augmentation: MCC not improved, recall traded for precision (Fig. 4). Feature sets differ little in either regime (Figs. 2-3). SMOTE is significantly better (Wilcoxon p<0.005, Sec. 6.3).
- **Stated limitations:** Absence of a report is not absence of a vulnerability (false negatives in labels); practitioners may know unreported vulnerabilities; default WEKA hyperparameters; SVM dropped because of tool problems; generalisation beyond three C systems not claimed (Sec. 6.4).
- **Critical assessment:** Clear, well-controlled demonstration that label timing dominates the outcome; data are released (github.com/kabinja/fse2019). Weaknesses: results are given mostly as box plots (Figs. 2-5) with few tabulated numbers; classifier and settings were chosen on RQ1 data, which is mild selection on the test releases; overlap of files between consecutive releases (unchanged-file leakage) is not separated from the labelling effect, so part of the "ideal" MCC of 0.77 on Linux may come from memorising files that are both unchanged and labelled with future knowledge; there is no LOC or size baseline. The count inconsistency (1,898 vulnerabilities vs 1,593 in Table 2) lowers confidence in the reporting.
- **Relevance to project:** High. This project's cross-version labels (bug-fix commits mapped to functions per version) must be "as-of" labels: for training version v_k, only fixes known before the release date of v_{k+1} (or the test cut-off) should count, otherwise the same leakage applies. The 0.77 to 0.08 MCC drop gives a magnitude for the possible error. It also supports reporting MCC and effort-aware metrics (top-k, inspection effort), which suits the comparison with SonarQube metrics. A labelling-regime ablation (realistic vs oracle labels) for Django/ActiveMQ would be cheap to add.

### Croft, Babar, Kholoosi, 2023, "Data Quality for Software Vulnerability Datasets", ICSE 2023 (read as arXiv 2301.05456v1)
DOI: 10.1109/icse48619.2023.00022

- **Access:** full_text
- **Task & granularity:** Data-quality audit of function-level vulnerability datasets (ISO/IEC 25012 attributes: accuracy, uniqueness, consistency, completeness, currentness) and the impact of each attribute on function-level vulnerability prediction.
- **Language & data:** C/C++ functions (Table II): Big-Vul 188,636 functions (5.78% vulnerable, NVD/CVE-linked); Devign 27,318 (45.61%, developer commits + manual filtering); D2A 1,295,623 (1.44%, static-analyser differential labels); Juliet 253,002 (36.77%, synthetic).
- **Representation:** Raw function source fed to LineVul (CodeBERT-based transformer). Duplicates detected with Allamanis' near-duplicate detector, minimum token count lowered to 5; type-3 clones with the same label counted as duplicates; consistency uses exact (type-1) clones with conflicting labels (Sec. IV-B/C).
- **Model:** LineVul (CodeBERT/RoBERTa fine-tuned), function-level prediction only.
- **Baselines:** None. The study compares one model under clean vs. unclean data, not across models.
- **Evaluation setup:** Random 80:10:10 train/validation/test split, 5 runs (Sec. III-D). Label accuracy: 70 random vulnerable samples per dataset manually checked by two raters (Cohen kappa 0.627). Accuracy impact measured on these samples as a holdout. Uniqueness impact: remove cross-set duplicates from the test set. Consistency impact: remove the non-vulnerable members of conflicting clusters from the test set only or from train+test. Currentness: data sorted by date into 10 partitions (train 4, tune 1, test 5 consecutive) with a Kendall trend test. Mann-Whitney U tests for significance. Metrics: precision, recall, MCC.
- **Duplication / leakage:** Central topic. Uniqueness (Table III): Big-Vul 0.830, Devign 0.899, D2A 0.021, Juliet 0.163. Duplicates arise mainly from "updated code" collected from multiple versions of the same repository, similar function sets, and renamed functions (Sec. IV-B). D2A averages 57 duplicates per unique function, and two of its repositories are forks (FFmpeg/Libav). Removing cross-set duplicates from the test set lowers MCC (Table V): Big-Vul 0.830 to 0.829 (0.0%), Devign 0.284 to 0.244 (-13.9%), D2A 0.774 to 0.141 (-81.7%), Juliet 0.909 to 0.814 (-10.4%). Recall drops more than precision (D2A recall 0.630 to 0.049). Latent (later-reported) vulnerabilities create inconsistent labels across versions (Fig. 4).
- **Metrics & key results:** Label accuracy on 70-sample checks (Table III): Big-Vul 0.543, Devign 0.800, D2A 0.286, Juliet 1.0, i.e. 20-71% of vulnerable labels wrong in real-world sets. Causes (Table IV): irrelevant changes, cleanup changes and mis-identified fixes (Big-Vul 25/28.1/46.9%). Training on corrected labels: precision on the holdout falls by 29% (Devign), 50% (Big-Vul) and 80% (D2A); recall is not significantly changed (Sec. IV-A). Consistency (Table III): Big-Vul 0.999, Devign 0.991, D2A 0.531, Juliet 0.750. D2A MCC is 0 unless training data are made consistent, then 0.748 (Table VI). Completeness 0.824-1.0 with no significant impact. Currentness (1 minus Jensen-Shannon divergence) 0.761-0.844, with no significant temporal degradation (Kendall p>0.05).
- **Stated limitations:** Manual accuracy check on 70 samples per dataset (±10% at 90% confidence); a single model (LineVul); attributes analysed one at a time (confounding); only C/C++ datasets with metadata (ReVeal excluded); ambiguous labels tentatively counted as correct (Sec. VI).
- **Critical assessment:** Valuable quantification with a reproduction package. Weaknesses: small manual sample; the accuracy-impact experiment has no negatives in its holdout, so MCC cannot be computed; a single model; random splits only, i.e. it measures leakage but does not test a realistic temporal split; the headline numbers are internally inconsistent ("17-99%" duplicated in the abstract while Devign's uniqueness of 0.899 implies about 10%; "up to 65%" in the conclusion vs 80% precision drop in Sec. IV-A). The D2A result conflates exact duplicates produced by the labelling process with ordinary leakage. Whether duplicates were removed in the temporal (currentness) experiment is not stated, so that test may itself be affected by leakage.
- **Relevance to project:** Very high. The main cause of duplication here, "updated code" from multiple versions of the same repository, is exactly the project's 22 Django / 5 ActiveMQ versions. Recommended practice to adopt: detect type-1 (exact, normalised) and type-3 near-duplicate functions with the same detector (it supports Python and Java); report metrics with cross-set duplicates removed from the test set; remove or resolve label-conflicting exact duplicates (the same function body labelled buggy in one version and clean in another), which are the latent-defect inconsistency in Fig. 4; audit a random sample of buggy-labelled functions for tangled/cleanup changes. Since CodeBERT (LineVul backbone) is one of the project's baselines, the -14% to -82% MCC range is a directly comparable magnitude.

### Ding, Fu, Ibrahim, Sitawarin, Chen, Alomair, Wagner, Ray, Chen, 2025, "Vulnerability Detection with Code Language Models: How Far Are We?" (PrimeVul), ICSE 2025 (read as arXiv 2403.18624v2)
DOI: 10.1109/icse55347.2025.00038

- **Access:** full_text
- **Task & granularity:** Function-level vulnerability detection with fine-tuned and prompted code LMs; new benchmark (PrimeVul) and evaluation protocol.
- **Language & data:** C/C++ functions. PrimeVul: 6,968 vulnerable and 228,800 benign functions from 755 projects and 6,827 commits, 140 CWEs, about 1:32 ratio (Sec. III-B, V-C). Temporal split (Table III): train 5,574/178,853, dev 699/24,731, test 695/25,216; paired subset 5,480 pairs. Comparison dataset BigVul (public split).
- **Representation:** Raw function text for CodeT5 (60M), CodeBERT (125M), UniXcoder (125M), StarCoder2 (7B), CodeGen2.5 (7B); GPT-3.5/GPT-4 via prompting and fine-tuning (Table IV). No graphs.
- **Model:** Fine-tuned code LMs (lr 2e-5; 10 epochs for <7B models, 4 epochs for 7B); UniXcoder used for class-weight and contrastive (CLR, class-aware CLR) variants; GPT-3.5 fine-tuned for 1 epoch on a 1:3 subsample.
- **Baselines:** Comparison across code LMs and against BigVul-trained/evaluated numbers; random guessing for pair-wise evaluation (Table VIII). No non-neural baseline (metrics, bag-of-words, static analyser).
- **Evaluation setup:** Label accuracy: 50 random vulnerable functions per benchmark manually checked by 3 annotators with majority vote (Sec. II-B). Leakage audit: exact copies after whitespace normalisation between test vulnerable functions and all training samples (Table II). PrimeVul split: chronological by commit date (oldest 80% train, 10% validation, newest 10% test), with all functions from one commit kept in the same split (Sec. IV-A). Metrics: accuracy, F1, VD-S = FNR at FPR<=0.5%, and pair-wise outcomes P-C/P-V/P-B/P-R. Single run per configuration; no variance reported.
- **Duplication / leakage:** Identifies two leakage types: "code copy" and "time travel" (Sec. II-C). Exact-copy share of test vulnerable functions also present in training (Table II): BigVul 12.7%, CVEFixes 18.9%, CodeXGLUE 0.6%, DiverseVul 3.3% (MD5 de-dup without whitespace normalisation missed these), PrimeVul 0.0%. Time travel: random splits allow training on future fixed versions and testing on older vulnerable versions, and put functions from the same multi-function fix commit on both sides. Mitigation: whitespace-normalised MD5 de-duplication; drop functions unchanged by the commit (identical pre/post hash); chronological, commit-grouped split. Only exact duplicates after normalisation are removed; near-duplicates are not.
- **Metrics & key results:** Label accuracy of vulnerable functions (Table I): SVEN 94%, CodeXGLUE/Devign 24%, VulnPatchPairs 36%, BigVul 25%, CrossVul 47.8%, CVEFixes 51.7%, DiverseVul 60% (last four quoted from Chen et al.); PrimeVul-OneFunc 86%, PrimeVul-NVDCheck 92%. Table V: StarCoder2 F1 68.26 on BigVul to 3.09 when the BigVul-trained model is tested on PrimeVul, and 18.05 when trained on PrimeVul. CodeBERT F1 62.88 (BigVul) to 4.49 (BV to PV) and 20.86 (PV to PV); its VD-S (FNR at FPR<=0.5%) is 81.77 on BigVul and 88.78 on PrimeVul. Accuracy stays about 95-97% in all settings. Pair-wise correct (P-C) on PrimeVul 1.06-3.01%. Class weights up to 40x: F1 21.43 to 26.28, VD-S about 88-91 (Table VI). CA-CLR: F1 24.46 (Table VII). GPT-4 CoT P-C 12.94 vs random 22.70 (Table VIII).
- **Stated limitations:** Label accuracy <100% (86-92%); VD-S depends on the chosen FPR tolerance r; OpenAI models run with default settings only (Sec. VI). The authors argue that single-function inputs may lack necessary context (interprocedural data flow).
- **Critical assessment:** Influential, with artifact released (github.com/DLVulDet/PrimeVul). Strengths: commit-grouped chronological split; normalised de-duplication; realistic class ratio; metrics that expose accuracy/F1 as misleading. Weaknesses: the BigVul vs PrimeVul gap mixes at least four factors (label noise, leakage, class ratio 1:32 vs BigVul's, distribution shift), so the drop from 68 to 3 F1 cannot be attributed to leakage alone; no ablation isolating each factor; single runs with no confidence intervals although the test set has only 695 positives; near-duplicates are not removed; OneFunc labelling biases positives towards single-function fixes; no graph-based or classical baseline, so "code LMs fail" is not compared with what simpler models achieve; label-accuracy figures for four datasets are reused from Chen et al.
- **Relevance to project:** High for protocol design. Directly reusable: whitespace/comment-normalised hashing of each function body; dropping functions unchanged between versions or reporting them separately; grouping all functions touched by one fix commit into the same split; chronological splits; reporting a fixed-FPR operating point (FNR@FPR<=x) and pair-wise buggy-vs-fixed evaluation in addition to F1/MCC. The paired evaluation suits Django/ActiveMQ well, because the pre-fix and post-fix versions of a function are available, and it directly tests whether CFG/DDG graphs separate them better than CodeBERT text embeddings. CodeBERT, one of the project's baselines, has VD-S of about 89% FNR, which sets expectations. The authors' call for interprocedural context also supports adding data-flow/call information beyond a single function.

### Chakraborty, Krishna, Ding, Ray, 2022 (online 2021), "Deep Learning based Vulnerability Detection: Are We There Yet?" (ReVeal), IEEE TSE (read as arXiv 2009.07235v1, Sept 2020 preprint; the final TSE version may differ)
DOI: 10.1109/tse.2021.3087402

- **Access:** full_text
- **Task & granularity:** Function-level vulnerability prediction; replication of VulDeePecker, SySeVR, Russell et al., Devign on realistic data, plus the ReVeal pipeline.
- **Language & data:** C/C++. New ReVeal dataset from Chromium (Bugzilla) and Debian kernel (security tracker): 18,169 functions, 9.16% vulnerable (Table 1). Also FFMPeg+Qemu (Devign): 22,361 functions, 45.02% vulnerable. Pre-trained baselines used their own datasets (Juliet, SARD/NVD, Draper). Labels: pre-patch versions of all functions changed by a security patch are vulnerable; post-patch versions and all unchanged functions of the touched files are clean (Sec. 3, Fig. 5).
- **Representation:** Code property graph (AST + CFG + data flow + PDG, Yamaguchi et al.). The extraction tool is not named in this version. Node features = one-hot node type concatenated with word2vec (100-d) embedding of the node's code fragment; 8-step GGNN; graph embedding = sum of node vectors (Sec. 4.1, Table 2).
- **Model:** ReVeal: GGNN pre-trained with a classification head, then SMOTE on graph embeddings, then a 3-layer MLP with triplet loss (cross entropy + projection loss on cosine distance + L2 regularisation) (Sec. 4.2).
- **Baselines:** VulDeePecker (BLSTM on slices), SySeVR (BGRU on slices), Russell et al. (CNN + random forest on tokens), Devign (GGNN on CPG, re-implemented because code was not available). Ablations: without GGNN, without SMOTE, and replacing the representation learner with random forest, SVM (RBF) or MLP (Table 7).
- **Evaluation setup:** 30 runs, each a random 80/10/20 train/validation/test split; median and IQR reported; non-parametric bootstrap test + A12 effect size (99% confidence, A12>=0.6) (Sec. 5.3). Scenario A: pre-trained models tested on real data. Scenario B: retrained on real data. Early stopping on validation F1. SMOTE applied to training data only (Algorithm 1). Metrics: accuracy, precision, recall, F1. The splits are random, not chronological or cross-project.
- **Duplication / leakage:** Duplicate rates (Table 4): Juliet with Russell preprocessing 68.63%; NVD+SARD 67.33% (VulDeePecker) and 61.99% (SySeVR); Draper 6.07/2.99%; ReVeal raw 0.6%, rising to 25.85% / 25.56% / 8.93% after VulDeePecker / SySeVR / Russell preprocessing; FFMPeg+Qemu raw 0.2%, rising to 19.58-22.10%. Slicing and abstract tokenisation create duplicates. The paper states that ReVeal "does not suffer from data duplication" because distinct inputs give distinct GGNN feature vectors (Sec. 6.3), which does not address near-duplicates. The dataset design itself includes the pre-patch (vulnerable) and post-patch (clean) versions of the same function, plus the unchanged functions of the file, under a random split, so near-identical pairs can fall on both sides of the split. This leakage is not analysed. Tangled-commit check: restricting to single-function patches drops ReVeal F1 to 26.33% (Sec. 7.2).
- **Metrics & key results:** Reported vs realistic F1: pre-trained models on real data drop F1 by about 73% on average; retrained models drop by about 54% (Sec. 6.1). Example: VulDeePecker precision 86.9% (paper) vs 11.12% (pre-trained, ReVeal data) vs 17.68% (retrained) (Table 3). Retrained F1 on ReVeal data (Table 3c, median): Russell 15.24, VulDeePecker 15.7, SySeVR 30.25, Devign 29.87; on FFMPeg+Qemu: 45.62 / 35.20 / 56.03 / 57.18. ReVeal (Tables 5-7): ReVeal data F1 41.25 (precision 30.91, recall 60.91), FFMPeg+Qemu F1 64.42. Ablations on ReVeal data: without GGNN F1 39.09 (A12 0.81); without SMOTE F1 22.44 (precision 46.23, recall 15.09); random forest on the same embeddings 25.32, SVM 39.85, MLP 36.42. The Devign reimplementation does not reproduce Devign's reported 73.26 F1.
- **Stated limitations:** Tangled commits (examined in Sec. 7.2); Devign re-implemented without original code or hyperparameters; F1/precision/recall depend on threshold and class ratio.
- **Critical assessment:** Important for its realistic labelling (all functions of the patched file, about 9% positive) and the 30-run statistics; code and data released (git.io/Jf6IA). Weaknesses: random function-level splits with pre-fix/post-fix pairs and copies of unchanged functions, so the main ReVeal numbers are themselves exposed to the cross-set near-duplicate leakage the paper criticises; the argument that GGNN embeddings make samples unique misunderstands leakage; F1 is the main metric, with no MCC/AUC or effort-aware metrics; the gain of the GGNN over no-GNN is small (41.25 vs 39.09 F1), and SVM on the same features gives 39.85, so most of the gain comes from SMOTE/imbalance handling rather than graph structure; t-SNE and centroid-distance arguments are qualitative. Later work (e.g. PrimeVul, Croft et al.) found ReVeal-style labels noisy.
- **Relevance to project:** High. Closest methodological template to the project: CPG/CFG+DDG per function, node features = node type + token embedding, GGNN, function-level labels from fix commits, and a dataset that includes unchanged functions of touched files. Lessons: (1) the useful ablation is graph vs no-graph (sum of node features without message passing): only about 2 F1 points here, so the project should test whether its CFG/DDG edges add anything over bag-of-nodes; (2) class-imbalance handling (SMOTE/class weights on training data only) changes F1 more than the architecture does; (3) including pre-fix and post-fix versions and unchanged copies across versions under random splits leaks, so cross-version splits plus de-duplication are needed; (4) report MCC/AUC besides F1. Python/Java are not covered.

### Li, Wang, Nguyen, 2021, "Vulnerability Detection with Fine-Grained Interpretations" (IVDetect), ESEC/FSE 2021 (read as arXiv 2106.10478v1)
DOI: 10.1145/3468264.3468597

- **Access:** full_text
- **Task & granularity:** Method-level vulnerability detection (graph classification), plus statement-level "interpretation": a PDG sub-graph from GNNExplainer.
- **Language & data:** C/C++ (Table 1): Fan et al. / Big-Vul (10,547 vulnerable, 168,752 non-vulnerable, 1:16); ReVeal (1,664 / 16,505, 1:9.9); FFMPeg+Qemu/Devign (10,067 / 12,294, 1:1.2).
- **Representation:** Program dependence graph per method (statements as nodes, control- and data-dependence edges); the PDG extraction tool is not named. Node features: sub-token sequence (GloVe + GRU), AST sub-tree (Tree-LSTM), variable names and static types (GloVe + GRU), and data/control-dependency context statements, combined by an attention BiGRU and summed over PDG neighbours (Sec. 3.1, Eq. 1).
- **Model:** Feature-attention GCN (FA-GCN) with spatial pyramid pooling, fully connected layers, and a trainable threshold; GNNExplainer edge masks for statement-level interpretation (Sec. 3.2, 4).
- **Baselines:** VulDeePecker, SySeVR, Russell et al., Devign, ReVeal (method level); ATT and GRAD explainers (statement level). No non-neural or metrics baseline.
- **Evaluation setup:** Vulnerable methods randomly split 80/10/10. Training set balanced by adding an equal number of non-vulnerable methods; tuning/test keep the original ratio. AutoML hyperparameter tuning on the tuning set for all models (Sec. 5.3). Cross-dataset: train on ReVeal + FFMPeg+Qemu, tune on 20% of Fan, test on the other 80%. Interpretation evaluated only on vulnerable methods correctly detected in the cross-dataset run, re-split 80/10/10; an interpretation counts as correct if any of its statements overlaps a deleted/modified fix line or depends on an added line (Sec. 5.3). Ranking metrics (nDCG@k, MAP@k, FR, AR) over the test list, plus AUC, precision, recall, F1. Single run; no variance or significance tests reported.
- **Duplication / leakage:** Not discussed. Random splits; Fan/Big-Vul contains vulnerable and fixed versions and known duplicates (12.7% exact-copy test leakage according to PrimeVul Table II). The "cross-dataset" test is not project-disjoint: Big-Vul's top projects include Chromium, QEMU and FFmpeg (LineVD Table 5), which are also the sources of ReVeal (Chromium) and FFMPeg+Qemu. Statement-level labels are derived using the same PDG dependencies the model uses.
- **Metrics & key results:** FFMPeg+Qemu (Table 3): AUC 0.84 vs ReVeal 0.79, Russell 0.79, Devign 0.77; nDCG@10 0.68 vs 0.50 (ReVeal); MAP@10 0.78 vs 0.38. Fan (Table 4): AUC 0.90 vs 0.82 (ReVeal/Russell). ReVeal data (Table 5): AUC 0.81 vs 0.74 (ReVeal). F1 (Table 6): FFMPeg+Qemu 0.65 vs 0.62 (ReVeal); Fan 0.35 vs 0.30; ReVeal 0.45 vs 0.40. Top-10 on FFMPeg+Qemu: 6 correct vs 5 for ReVeal (Table 2). Interpretation (Table 7): accuracy at 5 statements 0.67 (GNNExplainer) vs 0.59 (ATT, GRAD); MFR 3.5. Feature ablation on Fan (Table 9): AUC 0.75 (tokens only) up to 0.83 (+variables), 0.85 (+control dependencies), 0.90 (+data dependencies). Training-size sensitivity (Table 10): AUC 0.69 (40% training) to 0.90 (80%). Interpretation generation took 9 days on Fan.
- **Stated limitations:** C/C++ only; best-effort tuning of baselines; DL baselines only, no static-analysis tools; unseen vulnerabilities and dependency-induced mislocalisation (Sec. 6, 8).
- **Critical assessment:** Weak evidence by this group's standards: (1) random splits without de-duplication on datasets with known duplicates and label noise; (2) headline ranking metrics at top-1..10 depend on a handful of functions (e.g. 6 vs 5 correct in the top 10) and are reported from a single run with no variance; (3) the abstract claims 43-84% nDCG@10 improvement while the conclusion says 64-122%, an internal inconsistency; (4) the lenient interpretation-accuracy definition (any overlap with fix-related or dependent statements) inflates statement-level accuracy, and it is evaluated only on correctly detected methods; (5) the "cross-dataset" setting shares projects (Chromium, FFmpeg, QEMU); (6) the dependency context features appear to use knowledge of vulnerable statements during training (Sec. 2.2.2), and how this is avoided at test time is not fully specified; (7) LineVD's reimplementation of IVDetect obtained statement-level ROC-AUC of only 0.463. Replication data are linked ([10]), but the PDG tool and many details are unspecified.
- **Relevance to project:** Moderate. Its feature ablation (Table 9) is the most useful part: adding control dependencies then data dependencies to token/AST/variable features raised AUC from 0.83 to 0.85 to 0.90 under a leaky random split. The project can replicate this incremental ablation (tokens, then + CFG edges, then + DDG edges) under cross-version, de-duplicated splits to test whether the gain survives. Its rich statement features (sub-tokens, AST sub-tree, variable types) suggest node features for Joern graphs. The ranking metrics (nDCG/MAP over functions) are close to effort-aware defect-prediction evaluation, but should be computed on a full, realistic-ratio test version rather than a top-10 list.

### Hin, Kan, Chen, Babar, 2022, "LineVD: Statement-level Vulnerability Detection using Graph Neural Networks", MSR 2022 (read as arXiv 2203.05181v2)
DOI: 10.1145/3524842.3527949

- **Access:** full_text
- **Task & granularity:** Statement-level (line-level) vulnerability detection, formulated as node classification in a per-function graph, jointly with function-level classification.
- **Language & data:** C/C++ Big-Vul (300+ projects, about 10,000 vulnerable and 177,000 non-vulnerable functions per Sec. 4.2). Cleaned: comments removed, cosmetic-only changes dropped, 30 truncated functions removed, functions Joern cannot parse or without dependency edges removed. Final counts after cleaning not reported. Statement labels: deleted lines in the fix, plus lines control- or data-dependent on added lines (Sec. 4.2.1).
- **Representation:** Joern-extracted program dependence graph (control-dependence + data-dependence edges; CDG-only variant tested); Joern nodes grouped by line number, nodes without line numbers dropped (Sec. 4.5.3). Node features = frozen CodeBERT [CLS] embedding of each statement; separate CodeBERT embedding of the whole function.
- **Model:** LineVD: CodeBERT statement embeddings, then GAT layers over the PDG, then a shared MLP with the function-level CodeBERT embedding; statement outputs multiplied element-wise by the function-level prediction (a non-vulnerable function has no vulnerable lines) (Sec. 3.2.3). At most about 2 useful GNN layers (Sec. 6.2).
- **Baselines:** IVDetect (re-implemented, statement localisation via GNNExplainer); embedding ablation (Doc2Vec, averaged GloVe, CodeBERT) with an MLP; GNN ablations (GCN vs GAT, CDG vs PDG, with/without function-level branch, no-GNN).
- **Evaluation setup:** Random 80:10:10 split at function level; training set undersampled to roughly balanced at function level; validation and test keep the original imbalance (Sec. 4.2.2). Decision threshold tuned on validation F1. Hyperparameters via Ray Tune random grid search; mean of 10 seeds; Wilcoxon signed-rank tests on F1 (Sec. 4.3-4.4). Cross-project: leave-one-project-out for the top 10 projects (Sec. 4.5.4). No chronological split; the authors note time-based validation as a threat and argue cross-project evaluation mitigates it (Sec. 6.1).
- **Duplication / leakage:** Not addressed beyond removing cosmetic-only changes and truncated samples. No de-duplication of near-identical functions; random function-level split on Big-Vul, for which PrimeVul (Table II) later reported 12.7% exact-copy test leakage and about 25% label accuracy. The authors say within-project identifier names may help random-split results (Sec. 5.4).
- **Metrics & key results:** Table 2 (statement-level, random split): LineVD F1 0.360, recall 0.533, precision 0.271, ROC-AUC 0.913, PR-AUC 0.642 vs IVDetect F1 0.176, ROC-AUC 0.463. Table 1 ranked: MAP@5 0.760 vs 0.424; MFR 3.819 vs 8.192. Embeddings (Table 3, MLP): F1 Doc2Vec 0.064, GloVe 0.129, CodeBERT 0.150. Table 4 ablation: No GNN + Func F1 0.296, GAT+PDG+Func 0.360 (+24%, p<0.01), GAT+CDG+Func 0.304, GCN+PDG+Func 0.310; without the function branch, GAT+PDG 0.150 vs No GNN 0.129, while GCN variants (0.084/0.085) are below No GNN. Cross-project (Table 5): F1 0.250-0.333, ROC-AUC 0.903-0.928. Statement types (Table 6): best on function declarations (F1 0.68), worst on goto/break/continue (0.09-0.22).
- **Stated limitations:** Possibly sub-optimal hyperparameter search; intra-procedural context only (no inter-procedural information or macros); time-based validation not done; CodeBERT not pre-trained on C/C++; GNN over-squashing beyond about 2 layers (Sec. 6).
- **Critical assessment:** Code, data and models released. Concerns: (1) random splits on Big-Vul with noisy labels and known duplicates, so the absolute numbers are probably inflated; (2) most of the gain comes from the function-level gating (No GNN 0.129 to No GNN+Func 0.296), not from the graph (0.296 to 0.360); GCN on the same graph is worse than no GNN, so the benefit of graph structure depends on architecture; (3) Table 3's "CodeBERT" row is numerically identical to Table 4's "GAT+PDG" row and Table 3's "GloVe" row is identical to "No GNN", although RQ2 is described as an MLP experiment; this is an unexplained reporting inconsistency; (4) the dependency-based label heuristic marks lines dependent on added lines as vulnerable, using the same PDG that the model consumes, which can make the task partly circular, i.e. labels are defined via graph edges that the GNN sees; (5) no variance reported despite 10 seeds; (6) the IVDetect baseline (ROC-AUC 0.463, below chance) suggests a weak reimplementation; (7) cross-project ROC-AUC (about 0.92) is higher than the random-split one (0.913) while F1 is lower, which is not discussed.
- **Relevance to project:** Directly relevant on tooling: shows a Joern PDG pipeline (group Joern nodes by line, drop nodes without a line number, remove functions without dependency edges), which the project can mirror for Python/Java. It gives an ablation pattern to copy: no-GNN with the same node features vs GCN/GAT, CDG (control) vs PDG (control+data). Data-dependency edges helped here (CDG-only was worse). It also shows that Doc2Vec node embeddings are much weaker than CodeBERT (F1 0.064 vs 0.150), consistent with the project's baselines. Caution: its evaluation lacks leakage control and cross-version splits, so it should not be cited for magnitudes; only the relative ablation pattern is informative.

### Zeng, Zhang, Zhang, Zhang, 2021, "Deep Just-in-Time Defect Prediction: How Far Are We?", ISSTA 2021 (read as PDF from co-author L. Zhang's publication page)
DOI: 10.1145/3460319.3464819

- **Access:** full_text
- **Task & granularity:** Just-in-time (commit-level) defect prediction; replication and extension of DeepJIT and CC2Vec.
- **Language & data:** 310,370 commits (81,300 defect-inducing) from 6 projects, 2011-01-01 to 2020-12-01: QT (95,758, 15.16% defective) and OpenStack (66,065, 31.68%) in C++ per the paper; Eclipse JDT (13,348, 41.20%), Platform (39,365, 37.74%) and Gerrit (34,610, 8.64%) in Java; Go (61,224, 36.75%) (Table 1). RQ2 uses the latest 3 years per project after removing recent data.
- **Representation:** No graphs. DeepJIT: CNNs over commit message and code change. CC2Vec: hierarchical attention network over added/removed hunks. Baselines use Kamei's 14 change metrics (Table 7). The released DeepJIT and CC2Vec code abstracts each changed file to an "added_code removed_code" token (max 10 per commit), i.e. effectively a count of changed files (Sec. 3.3.1, Fig. 3).
- **Model:** DeepJIT, CC2Vec (GitHub and paper variants), DBN-JIT, LR-JIT (Kamei logistic regression), and the proposed LApredict = logistic regression on the single feature LA (lines added).
- **Baselines:** LR-JIT and DBN-JIT (traditional), plus the single-feature LApredict baseline. All 14 single-feature logistic regressions (Fig. 7).
- **Evaluation setup:** Labels from SZZ (keyword-identified fix commits, diff + blame), with Kim/McIntosh filtering. Recent data removed by the median defect-fix delay (e.g. 526 days for QT) to reduce verification latency (Sec. 3.1). RQ1 replicates the original 5-fold cross-validation with 16 runs (Table 2). RQ2/RQ4: chronological split, earliest 80% of commits for training and latest 20% for testing (Sec. 3.3.2). Cross-project: train on the other 5 projects and test on the same test split. Feature analysis by 10-fold CV inside the training data only, "to prevent data leakage" (Sec. 3.3.3). Main metric AUC; FDR/ACC at fixed recall (Fig. 5). After RQ1 a single run is reported, because the 16-run std was <0.003.
- **Duplication / leakage:** Temporal: chronological 80/20 split and removal of recent commits to limit label latency; feature selection done only on training data. Code duplication across commits is not discussed. The chronological split ignores the fact that a commit is only labelled once its fix is found, i.e. training labels may include fixes made after the test period starts (as-of labelling is not enforced).
- **Metrics & key results:** Replication (Table 2, 16 runs): DeepJIT_GitHub mean AUC 0.7705 vs DeepJIT_Paper 0.7438; CC2Vec_GitHub 0.7841; std <=0.0030. Ablation (Table 4): CC2Vec code vector alone AUC 0.4865. Extended dataset, within-project (Table 5/8, mean AUC): DeepJIT 0.7065, CC2Vec 0.7055, LR-JIT 0.6726, DBN-JIT 0.6847, LApredict 0.7246. Cross-project mean: DeepJIT 0.6808, CC2Vec 0.6771, LR-JIT 0.6490, DBN-JIT 0.6532, LApredict 0.7246 (identical, because AUC of a monotone single-feature model is independent of training data). Per project, LApredict reaches 0.7438 on QT vs best DL 0.6936 (Sec. 3.3.4). Time (Table 9): LApredict trains in about 0.011 s vs about 917-925 s for DeepJIT/CC2Vec. Early-period AUCs (Table 6) differ from late-period ones (e.g. DeepJIT on JDT 0.7491 vs 0.6701). More history does not monotonically help (Fig. 6).
- **Stated limitations:** SZZ label noise (argued not to affect the comparison); implementation bugs; AUC as main metric with FDR/ACC/recall as supplement (Sec. 5).
- **Critical assessment:** Convincing "strong simple baseline" result with code and data released (github.com/ZZR0/ISSTA21-JIT-DP). Caveats: (1) AUC is threshold-free and favours size-like rankers; effort-aware metrics such as Popt or recall@20%LOC were not reported, and those penalise LA-style rankers because large commits cost more to inspect, so the LApredict advantage could shrink or reverse under effort-aware evaluation; (2) after RQ1 there is a single run with no significance tests; (3) LApredict's identical WP/CP AUC is by construction, not robustness; (4) no MCC or F1 at a threshold; (5) SZZ labels without as-of control. Still, it shows that "added_code" placeholders, i.e. a file count, outperform the semantic encoder, which is a warning about attributing gains to semantics.
- **Relevance to project:** Strong caution for the graph models: size proxies (function LOC, number of CFG nodes/edges, cyclomatic complexity) can match learned representations. The project should include LOC-only / node-count-only logistic regression and the SonarQube metrics model as baselines, and ablate graph size, e.g. by checking whether a GNN beats logistic regression on |V| and |E|. It also motivates reporting effort-aware metrics alongside AUC/MCC, a chronological split with training-only feature selection, and multiple seeds. JIT task differs from the project's per-function cross-version setting, so the magnitudes do not transfer directly.
