# Network/dependency graphs and network embeddings for defect prediction — reading notes

Theme: inter-module dependency or network graphs and learned network embeddings for defect prediction, and whether the network-metric advantage survives realistic (forward-release or cross-version) evaluation.

Access: 5 of 7 were read in full (Zimmermann & Nagappan 2008 from the author PDF; Tosun et al. 2009 from the PROMISE PDF; Premraj & Herzig 2011 from the Saarland PDF; DeMuVGN arXiv v1; Bryan & Moriano 2023 PLOS). node2defect (ASE 2018) and GCN2defect (ISSRE 2021) are **abstract only**.

## Per-paper notes

### Zimmermann & Nagappan, 2008, Predicting defects using network analysis on dependency graphs, ICSE 2008
DOI: 10.1145/1368088.1368161

- **Access:** full_text
- **Task / granularity:** Post-release defect prediction at binary level (DLL/EXE) for one release of Windows Server 2003: escrow (critical-binary) ranking, correlation, linear regression for defect counts, and logistic regression for defect-proneness.
- **Language & data:** Windows Server 2003 (C/C++, with some .NET), one release, proprietary. The number of binaries and the defect ratio are not reported. Escrow-list size is hidden; escrow recalls are truncated to multiples of 5% (Sec. 5.1). Data are available only on request to the authors (Sec. 5.4).
- **Representation:** System-wide dependency graph from Microsoft's MaX tool at function level (calls, imports/exports, RPC, COM, registry access, data dependencies), lifted to binary level, unweighted, self-edges allowed (Sec. 4.1). Network measures computed with UCINET 6 (Sec. 4.2): ego-network measures for In/Out/InOut neighbourhoods (Table 1: Size, Ties, Pairs, Density, WeakComp, Brokerage, EgoBetween...), structural holes (EffSize, Efficiency, Constraint, Hierarchy), and global centralities (degree, closeness, dwReach, eigenvector, information, betweenness). Code-metric control set (Table 2): functions, global variables, Lines, Parameters, FanIn, FanOut, cyclomatic complexity (total/max per binary), and OO metrics.
- **Model:** PCA (components explaining >95% variance: 15 for SNA, 6 for METRICS, 20 for SNA+METRICS), then multiple linear regression or binary logistic regression with threshold 0.5 (Sec. 5.3).
- **Baselines:** Non-OO complexity metrics only (METRICS); OO metrics excluded from regression. The authors state there is no 'best existing technique' to compare against (Sec. 5.4).
- **Evaluation setup:** Single release. 50 random 2/3-1/3 splits of binaries per experiment, 300 models in total (Sec. 5.3, Fig. 6). Within-release random split; no cross-version, chronological or cross-project evaluation. Labels: post-release defects mapped to binaries, assuming the fix location equals the defect location (Sec. 5.4). Wilcoxon signed-rank tests between feature sets.
- **Duplication / leakage:** Not discussed. Because the whole graph is computed on the full release before splitting, centrality measures of test binaries depend on the entire system. This is not a label leak, but the evaluation is purely within-release.
- **Key results:** Escrow recall (Table 3): GlobalInClosenessFreeman 0.60 and GlobalIndwReach 0.60, versus 0.30 for the best complexity metrics (TotalParameters, TotalComplexity, TotalLines, ...). Spearman correlation with defects (Table 4): network measures up to about 0.46 (EgoInOut Size .462, Degree .462, EffSize .466); complexity metrics are slightly higher (TotalLines .516, TotalParameters .521, TotalComplexity .509). Linear regression (Sec. 5.3, Fig. 7): Spearman between predicted and actual about 0.50 for SNA and for METRICS alone, about 0.60 for SNA+METRICS (Wilcoxon p<0.01). Logistic regression (Fig. 8): precision about 0.70 for all three sets; recall about 0.60 for METRICS and about 0.70 for SNA and SNA+METRICS, the headline '+10 points recall'. Results are read from boxplots; exact values are not tabulated.
- **Stated limitations:** Fix location assumed to equal defect location; results may not generalise beyond Windows, or even to other Microsoft products; complexity metrics chosen as the benchmark because no best technique exists (Sec. 5.4).
- **Critical assessment:** Single proprietary system, single release, random splits only. The data are not public and the number of binaries is not reported. Precision and recall come from a fixed 0.5 threshold; no AUC, MCC or effort-aware measure is reported. The 'recall +0.10' gain comes at roughly equal precision, which may partly be a threshold or calibration effect rather than better ranking. Correlations show complexity metrics at least as strong as network measures (Table 4). The baseline is a small code-metric set without process or churn metrics. Influential but weak evidence for deployment claims; the paper itself frames it as one piece of the puzzle.
- **Relevance to project:** Origin of the network-metric hypothesis that the project's graph features implicitly test. Its graphs are inter-module (binary-level), unlike the project's intra-procedural Joern CFG+DDG per-function graphs. Its UCINET ego/global measure set (Table 1) is a ready template for cheap handcrafted graph statistics: Joern call graphs could provide a module-level network baseline for Django/ActiveMQ. It shows why the project must use cross-version splits: its evidence is entirely within-release random split.

### Tosun, Turhan & Bener, 2009, Validation of network measures as indicators of defective modules in software systems, PROMISE 2009
DOI: 10.1145/1540438.1540446

- **Access:** full_text
- **Task / granularity:** Replication and extension of Z&N. Binary defect classification at function level for 3 small embedded C projects and at source-file level for 2 Eclipse releases.
- **Language & data:** AR3, AR4, AR5 (embedded white-goods controller software, C; PROMISE): 63, 107 and 36 functions, defect rates 0.12, 0.18 and 0.20. Eclipse 2.0 and 2.1 (Java, file level): 6,729 and 7,888 files, defect rates 0.013 and 0.004 as printed in Table 1. These are far below the usual PROMISE Eclipse rates, unexplained, and Eclipse labels combine pre- and post-release defects (Sec. 3, 5.1). 29 code metrics for AR and 198 for Eclipse; 23 network metrics (Table 1).
- **Representation:** Static caller-callee call graph between methods extracted with the authors' tool Prest (NxN matrix). Network metrics computed with UCINET 6 (ego and global, Appendix B). For Eclipse, method-level network metrics were aggregated to files (Sec. 3.2-3.3). Extension: CGBR, which weights each module's metrics by its PageRank on the call graph, normalised to [0.1, 1.0], 40 iterations (Sec. 4.2.1).
- **Model:** (1) Replication: logistic regression on PCA components (>95% variance). (2) Extension: Naive Bayes on log-filtered metrics, optionally CGBR-weighted.
- **Baselines:** Complexity metrics (CM: McCabe, Halstead, LOC) versus network metrics (NM) versus both (ALL); CM+CGBR and ALL+CGBR.
- **Evaluation setup:** Replication: 50 random 2/3-1/3 splits within each dataset (Sec. 4.1). Extension: leave-one-project-out within each data source. One project is the test set; training uses a random 90% of the other projects of the same source, repeated 100 times, giving 500 iterations (Sec. 4.2). For Eclipse this means training on 2.1 to predict 2.0 and on 2.0 to predict 2.1: a cross-version setup including backward-in-time prediction. For AR it is cross-project within one company.
- **Duplication / leakage:** Not discussed. The Eclipse cross-release Naive Bayes setup includes backward prediction (2.1 to 2.0) and makes no mention of files unchanged between releases.
- **Key results:** Logistic regression, random splits (Table 3). Small projects, average pd/precision/pf/bal: CM 47/41/12/62, NM 32/33/14/51. Eclipse average: CM 69/50/14/75, NM 70/59/21/73, ALL 70/54/16/76. Naive Bayes cross-release (Table 5, Eclipse average pd/precision/pf/bal): CM 76/64/42/66, NM 70/59/49/59, ALL+CGBR 75/65/40/67. Small projects (Table 4 average): CM 79/72/30/74, NM 39/45/48/45, CM+CGBR 77/79/20/78. So in the cross-release setting NM alone is worse than CM on every Eclipse average measure; the combination with CGBR gives at most 1 bal point over CM.
- **Stated limitations:** Granularity differs between data sources (function versus file); pre- and post-release defects are used interchangeably (AR has only pre-release test defects, Eclipse has both) (Sec. 5.1).
- **Critical assessment:** Tiny AR datasets (36-107 instances), so results there are very noisy. No variance or significance tests are reported despite 50 or 500 runs; only averages are given. The Eclipse defect rates in Table 1 look inconsistent with the PROMISE Eclipse data and are unexplained. The 'network metrics help in large systems' conclusion rests on NM roughly tying CM on 2 Eclipse releases, not on NM beating CM. Accuracy-type measures (pd, pf, bal) at a fixed threshold; no AUC or MCC. Prest is open source; the data are PROMISE plus self-extracted graphs, not clearly released.
- **Relevance to project:** First evidence that network metrics computed from a static call graph (the same kind of inter-procedural structure Joern exposes) do not beat code metrics when trained on one Eclipse release and tested on another. Directly relevant to CVDP on Django/ActiveMQ. CGBR (PageRank-weighting of metrics) is a cheap way to inject call-graph structure into SonarQube-style metric baselines. Shows how granularity mismatch (method-level graphs aggregated to files) is a confound, which also matters when mapping Joern per-function graphs to file-level labels.

### Premraj & Herzig, 2011, Network versus code metrics to predict defects: a replication study, ESEM 2011
DOI: 10.1109/esem.2011.30

- **Access:** full_text
- **Task / granularity:** External replication of Z&N. File-level binary classification (defect-prone or not) of post-release defects. Regression is explicitly not replicated (Sec. IV-A).
- **Language & data:** Java: JRuby 1.0/1.1 (517/550 files), ArgoUML 0.24/0.26 (1,480/1,752 files), Eclipse 2.1/3.0 (7,900/6,614 files) (Table I). Defect ratios are not reported in the text. Post-release bugs: for JRuby and ArgoUML, mined from commit messages via regex plus bug-tracker validation, counting reports filed after the release and before the next one; for Eclipse, the Zimmermann et al. PROMISE data (Sec. III-C).
- **Representation:** Dependencies from Java bytecode analysis (method calls and object usages), class-to-file mapping via JDT, file-level dependency graph. About 58 UCINET network metrics (ego for in/out/undirected, structural holes, centralities; Table II). Information centrality was dropped for Eclipse because UCINET crashed. Code metrics: 8 metrics from SciTools Understand chosen to mirror Z&N (Table II).
- **Model:** R caret: kNN, logistic regression (multinom), Naive Bayes, rpart, SVM-RBF, treebag. Preprocessing: near-zero-variance removal, correlation filter ρ>0.9, centring and scaling (PCA tried but worse). tuneLength=5 (Sec. V). For each setting the best model per metric set is plotted.
- **Baselines:** Code metrics (8) versus network metrics (about 58) versus combined.
- **Evaluation setup:** Three setups (Sec. IV). (1) Stratified repeated holdout within a single release: 300 times 66/34. (2) Forward-release (cross-version): train on the older release and test on the next (JRuby 1.0 to 1.1, ArgoUML 0.24 to 0.26, Eclipse 2.1 to 3.0). (3) Cross-project on the latest releases (all 6 ordered pairs). Statistics: Kruskal-Wallis for holdout and ANOVA across models for forward and cross-project. Measures: precision, recall, F-measure.
- **Duplication / leakage:** Not discussed explicitly. The forward-release split avoids training on future data, but unchanged files between consecutive releases are not identified or removed. Code metrics of unchanged files are identical across releases, and their network metrics are near-identical. Holdout within a release is the setting where network metrics win.
- **Key results:** Holdout (Sec. VI, Fig. 2): network metrics beat code metrics in every project and measure (Kruskal-Wallis p<.0001). Mean precision with network metrics about 0.8 for JRuby and about 0.6 for Eclipse; recall about 0.6 for JRuby and ArgoUML. Combined is better than network in only 4 of 18 cases. The authors put the network gain at roughly 20-25% versus about 10% in Z&N (Sec. X). Forward-release (Sec. VII, Fig. 3): no statistically significant difference between code, network and all (ANOVA) for JRuby, ArgoUML or Eclipse. Cross-project (Sec. VIII, Fig. 4): no significant differences except Eclipse to JRuby, where code metrics gave significantly lower F-measure. Exact numbers are shown only in figures, not tables.
- **Stated limitations:** Heuristic post-release bug mapping; the small code-metric set (8, to mirror Z&N) may understate code metrics (Sec. XI).
- **Critical assessment:** The strongest piece of evidence in this group, and the reason network-metric claims should be checked under realistic splits. Weaknesses: one forward pair per project (3 pairs total), so the forward and cross-project tests have very little power; 'no significant difference' is not equivalence. The code-metric baseline is deliberately weak (8 metrics), which if anything favours network metrics, yet they still do not win forward. Only best-model plots; F-measure, precision and recall only, with no AUC, MCC or effort-aware measures. Data and scripts were released on PROMISE (Sec. V); current availability not checked.
- **Relevance to project:** Central to the project's framing. It shows that a representation's advantage under within-release random splits can vanish under forward-release (CVDP) evaluation, exactly the setting the project uses for Django (22 versions) and ActiveMQ (5 versions). It supports the hypothesis that random-split gains partly reflect instance similarity (leakage-like effects), which the project's duplicate/unchanged-code analysis can quantify directly. It also argues for reporting graph features versus SonarQube metrics on equal cost and complexity terms.

### Qu et al., 2018, node2defect: using network embedding to improve software defect prediction, ASE 2018 (short paper, pp. 844-849)
DOI: 10.1145/3238147.3240469

- **Access:** abstract_only
- **Task / granularity:** From the abstract: defect prediction using class-level nodes of a Class Dependency Network. Classification granularity is presumably class or file but is not stated in the abstract.
- **Language & data:** Abstract: 15 open-source programs. Language, versions, instance counts and defect ratios: not available (abstract only).
- **Representation:** Abstract: Class Dependency Network (CDN), with node2vec embeddings learned on the CDN and concatenated with traditional software engineering metrics. Extraction tool, edge types and embedding dimension: not available.
- **Model:** Abstract: a classifier on node2vec embeddings plus traditional features; classifier type not stated.
- **Baselines:** Abstract: 'the state-of-the-art approach'; identity not stated.
- **Evaluation setup:** Not available (abstract only). Split type unknown.
- **Duplication / leakage:** Not available (abstract only).
- **Key results:** Abstract: on average node2defect improves the state-of-the-art approach by 9.15% in F-measure. No other numbers available.
- **Stated limitations:** Not available (abstract only).
- **Critical assessment:** Full text not accessible (ACM closed; the ResearchGate copy refuses automated access). F-measure-only headline in the abstract. node2vec embeddings are transductive: they are learned per graph and are not aligned across versions, so cross-version use needs embedding alignment (Cohen et al. 2022 address exactly this). Whether the evaluation used within-version random splits cannot be verified here. Supplementary code and data are reportedly on Zenodo record 4624751 (shared with the authors' follow-up EMSE study); not verified.
- **Relevance to project:** Canonical 'learned network embedding' paper. Relevant as a baseline family (node2vec on a call or dependency graph extracted by Joern for Django/ActiveMQ). For CVDP, embeddings of different versions live in different spaces, a practical obstacle the project must handle if it adds module-level embeddings.

### Zeng et al., 2021, GCN2defect: Graph Convolutional Networks for SMOTETomek-based Software Defect Prediction, ISSRE 2021, pp. 69-79
DOI: 10.1109/issre52982.2021.00020

- **Access:** abstract_only
- **Task / granularity:** From the abstract: class-level defect prediction as node classification on a Class Dependency Network.
- **Language & data:** Abstract: eight open-source programs. Language, versions, sizes and defect ratios: not available.
- **Representation:** Abstract: CDN, with node2vec structural embeddings concatenated with traditional code features as initial node attributes, then a GCN for deeper class representations.
- **Model:** Abstract: GCN node classifier with SMOTETomek resampling for class imbalance.
- **Baselines:** Abstract: 'the state-of-the-art approach'; identities not stated.
- **Evaluation setup:** Not available (abstract only). It is unknown whether the GCN was trained transductively on one version's graph with random node splits.
- **Duplication / leakage:** Not available (abstract only).
- **Key results:** Abstract: on average GCN2defect improves the state-of-the-art by 6.84% to 23.85% in F-measure. No other numbers available.
- **Stated limitations:** Not available (abstract only).
- **Critical assessment:** Full text not accessible (IEEE closed; no preprint found). Headline is F-measure-only. Where SMOTETomek was applied (training only, or also affecting evaluation) cannot be checked. A GCN on a single version's dependency graph is typically trained transductively, so test nodes' features are visible during message passing and neighbour labels leak via graph homophily. Whether this occurs here cannot be verified from the abstract. Its journal extension CGCN (Zhou et al., IST 2022) is used as a baseline by DeMuVGN.
- **Relevance to project:** Representative of GNN-on-dependency-graph defect prediction (module-level, transductive). Contrasts with the project's graph-level classification of per-function Joern CFG+DDG graphs. It is the kind of method that must be re-evaluated under a cross-version split with unchanged/duplicate code controlled.

### Qiao, Gong, Zhao, Wang & Wei, 2024, DeMuVGN: Effective software defect prediction model by learning multi-view software dependency via graph neural networks, arXiv preprint (v1 read; v2 of 7 May 2025 is a withdrawal notice)
DOI: 10.48550/arxiv.2410.19550

- **Access:** full_text
- **Task / granularity:** File-level binary defect prediction as node classification on a per-version file dependency graph. Within-project (WPDP) and cross-project (CPDP) contexts.
- **Language & data:** Java. 8 Apache projects, 20 versions (Table 1): ActiveMQ 5.0.0/5.1.0/5.2.0/5.3.0/5.8.0 (1,869-2,339 files, 5.88-15.07% defective), Camel 1.4.0/2.9.0/2.10.0/2.11.0, Groovy 1.5.7, HBase 0.95.0/0.95.2, Hive 0.9.0, JRuby 1.1/1.4/1.5, Lucene 2.3.0/2.9.0, Wicket 1.3.0.beta2/1.5.3. Defect ratios range from 2.13% to 26.92%. Datasets follow Yatish et al. (post-release defects). Node features: 65 metrics (54 Understand code metrics, 5 process, 6 ownership; Table 2).
- **Representation:** Code Dependency Graph (CDG): file-level directed graph from SciTools Understand data and call dependencies, edge weight = number of data plus call dependencies (Eq. 1). Developer Dependency Graph (DDG): mutual edges between files sharing a developer, weighted by the number of shared developers (Eq. 2). Developer identity is established 'by comparing the committer from the commit reports and the assignee from the corresponding defect reports' (Sec. 4.2.1). Multi-view graph (MSDG) = CDG weights + DDG weights (Eq. 3). Out-edge weights normalised per node. 60 graphs in total.
- **Model:** Bidirectional Gated GNN (BiGGNN): forward and backward sum aggregation, gated fusion, GRU update, K hops, MLP classifier, cross-entropy. SMOTE in embedding space on training nodes; synthetic nodes copy the source node's edges (Sec. 3.2). Hyperparameters from RandomizedSearchCV (Table 4).
- **Baselines:** WPDP: LR, NB, RF, SVM, XGBoost (all with SMOTE), CGCN (GCN extension of GCN2defect), DP-CNN, DBN. CPDP: DSSDPP, CGCN, MNB, TCBoost, VCB-SVM. Ablations: CDG-BiGGNN, DDG-BiGGNN, BiGGNN without SMOTE.
- **Evaluation setup:** WPDP: random 70/15/15 node split within the same version, 100 out-of-sample bootstrap repetitions (Sec. 4.2.2). The graph contains all nodes of the version, so the setting is transductive. CPDP: train and validate (80/20) on the latest version of another project and test on all nodes of the target version, 20 bootstraps times 7 source projects. No cross-version (older to newer release of the same project) experiment, even though ActiveMQ, Camel, JRuby and others have multiple versions. Wilcoxon signed-rank with Bonferroni correction and Cliff's delta. Measures: AUC, Recall, Brier, PF, F1 (medians reported).
- **Duplication / leakage:** Not discussed. Potential leakage channels (my assessment): (a) the DDG uses assignees of defect reports to define developer edges, so the defect reports that produce the labels also shape graph structure; (b) the WPDP random node split is transductive, letting test nodes participate in message passing; (c) Table 9 shows label homophily of neighbours is the mechanism the authors credit for the gains.
- **Key results:** RQ1 (Table 5 averages): DeMuVGN AUC 0.966, Recall 0.821, F1 0.902; CDG-BiGGNN AUC 0.935, F1 0.791; DDG-BiGGNN AUC 0.930, F1 0.781. ActiveMQ-5.0.0 DeMuVGN AUC 0.962, F1 0.953; ActiveMQ-5.8.0 AUC 0.986, F1 0.989. RQ2 (Table 7 averages): AUC/F1 for DeMuVGN 0.966/0.905, CGCN 0.854/0.731, RF 0.825/0.432, XGBoost 0.816/0.452, DBN 0.652/0.690, DP-CNN 0.769/0.447. RQ3: SMOTE adds +16.9% F1 over BiGGNN (Sec. 5.3). RQ4 CPDP (Table 8 averages): DeMuVGN AUC 0.982, F1 0.838; DSSDPP AUC 0.790, F1 0.650. My consistency check: many reported F1 values exceed the maximum F1 possible for the reported recall, 2R/(1+R) attained at precision 1. Examples: ActiveMQ-5.0.0 recall 0.852 allows F1 ≤0.920 but 0.953 is reported; HBase-0.95.0 recall 0.605 allows ≤0.754 but 0.993 is reported; the average recall 0.821 allows ≤0.902 against 0.902 reported. This suggests F1 is a weighted or macro average rather than defective-class F1, or a reporting error.
- **Stated limitations:** Developer dependency ignores developer code quality; naive weight summation for view fusion; CPDP benefit assumed from WPDP; only data and call dependencies (control dependencies suggested as future work); evaluation-metric choice; Java only (Sec. 7).
- **Critical assessment:** Weak evidence. (1) v2 on arXiv is a withdrawal; the listing comment says the paper 'is not comprehensive enough' (arXiv listing), so the claims are unrefereed and withdrawn. (2) F1 values are internally inconsistent with recall (see above), so F1 comparisons, including the 17.4-45.8% headline gains, are unreliable. (3) Within-version transductive random splits, with defect-report-derived graph edges, form a plausible label-leakage path. AUC 0.98-1.00 in CPDP (e.g. Camel-2.11.0 AUC 1.000, Table 8) is implausibly high for file-level defect prediction and should be treated as a warning sign. (4) No cross-version evaluation despite multi-version data. (5) Baselines like SVM with F1 of 0.000-0.12 on several datasets suggest poorly tuned baselines. (6) Code is linked (github.com/DeMuVGN/DeMuVGN, footnote p. 17); not checked.
- **Relevance to project:** Directly overlaps the project's data: 5 ActiveMQ versions (5.0.0, 5.1.0, 5.2.0, 5.3.0, 5.8.0) with file counts and defect ratios (Table 1), useful to cross-check the project's ActiveMQ labels. It is a cautionary example of how graph-based gains can arise from transductive within-version splits and label-derived edges. The project's leakage-controlled CVDP evaluation would be the natural test of whether such multi-view gains survive. Its call for control dependencies (Sec. 7) is what Joern CFG/CDG+DDG provide, though at function level rather than inter-file.

### Bryan & Moriano, 2023, Graph-based machine learning improves just-in-time defect prediction, PLOS ONE 18(4): e0284077
DOI: 10.1371/journal.pone.0284077

- **Access:** full_text
- **Task / granularity:** Just-in-time (change-level) defect prediction framed as edge classification on a developer-file bipartite contribution graph. An edge is a change.
- **Language & data:** Tian et al. (QRS 2020) dataset: 18 projects, of which 14 were used (POI, Pig, Velocity, Xerces-C dropped for missing commits). Java plus one C++ project in the original dataset. Includes ActiveMQ: 10,213 changes, 2005-2020, 43.34% positive in training and 43.27% in testing (Table 3). Positive rates range from 0.26% (HBase) to 47.58% (Hadoop). Labels: SZZ Unleashed, 'early exposed defects' with θ = min(4 weeks, 1% of project duration) (Sec. 3.2).
- **Representation:** Undirected weighted bipartite developer-file graph from git logs (weight = number of commits), projected onto developers (Neo4j GDS). Setting 1: developer centralities (degree, betweenness, closeness, harmonic, PageRank). Setting 2: Louvain community plus node2vec embedding (walk length 80, context 10, p=q=1, d=128). Features come only from the developer side of each edge (Fig. 2 caption).
- **Model:** Logistic regression, random forest and XGBoost; SMOTE (k=5) on training data; grid search with stratified 10-fold CV (Sec. 3.3-3.4).
- **Baselines:** Random-forest JIT baseline of Tian et al. 2020 using software change metrics. Its numbers appear to be quoted from that paper rather than re-run on the same split (not stated explicitly; the AUC-PR column is '—' because 'this metric was not computed in the state-of-the-art baseline').
- **Evaluation setup:** Random 75/25 split of labelled changes (Sec. 3.3), not time-ordered, single split, no repetitions. Precision, recall and F1 at the F1-optimal threshold from the PR curve (Sec. 3.5); MCC at threshold 0.5. The graph is a static snapshot built from the git log (Sec. 5.2).
- **Duplication / leakage:** Not discussed as leakage. The authors acknowledge using a static snapshot whose features 'do not generalize to unseen nodes and/or edges' and that temporal information was not assessed (Sec. 5.2). My assessment: a random, non-chronological split, a graph and embeddings built over the whole history including test-period commits, and an F1 threshold apparently chosen on the evaluation PR curve all inflate results. Because features are developer-only, the model largely learns per-developer defect base rates, which random splits make easy.
- **Key results:** Table 4 means over 14 projects. Setting 1 XGBoost: P 0.7341, R 0.8239, F1 0.7755, MCC 0.5234, AUC-PR 0.7993. Setting 1 RF: F1 0.7724, MCC 0.5316. Setting 1 LR: F1 0.5871, MCC 0.3393. Setting 2 XGBoost: F1 0.7748, MCC 0.5234. Baseline (Tian et al. RF): P 0.4673, R 0.7644, F1 0.3083, MCC 0.5141. Headline: +152% F1 (0.3083 to 0.7755) but only +3% MCC (0.5141 to 0.5316), and LR is below the baseline on MCC.
- **Stated limitations:** SZZ mislabelling; static graph snapshot without temporal evaluation; topology only, with no change or developer attributes; average-only reporting hides per-project detail; default graph-algorithm parameters; AUC-style metric caveats (Sec. 5.1-5.7).
- **Critical assessment:** The F1 gain is largely an artefact of differing thresholds and protocols; the MCC gain of 0.5141 to 0.5316 is negligible and untested statistically. The baseline F1 0.3083 with P 0.4673 and R 0.7644 suggests averaging over heterogeneous projects or protocols, so the comparison is not like-for-like. The split is random, single-run, with no variance and no time ordering, which is unrealistic for JIT, where chronological evaluation is standard (McIntosh & Kamei 2017 is cited). Data and code are released (GitHub: lining-nwpu/JiTReliability, jtbryan/defect-prediction).
- **Relevance to project:** Peripheral in task (JIT rather than file or function CVDP) but includes ActiveMQ. It is another example of a graph-feature gain obtained under a random rather than temporal split, supporting the project's emphasis on chronological or cross-version, leakage-controlled evaluation. It also shows why MCC should be reported alongside F1, as the project plans.

## Synthesis

Across the three classic studies the pattern is consistent: the advantage of inter-module network metrics over code metrics depends on the evaluation protocol. Zimmermann & Nagappan (2008) reported higher recall (about 0.70 versus 0.60 at about 0.70 precision, Fig. 8) and doubled escrow recall (0.60 versus 0.30, Table 3) on one Windows Server 2003 release, using 50 random 2/3-1/3 splits. Yet their own correlations show complexity metrics at least as strongly associated with defects (Table 4). Premraj & Herzig (2011) reproduced and even enlarged the gain under stratified random holdout on JRuby, ArgoUML and Eclipse. However, they found no statistically significant difference between code, network and combined metrics under forward-release prediction (older to next release) and cross-project prediction (Sec. VII-VIII). Tosun et al. (2009) found network metrics useless on tiny embedded projects. On Eclipse they found them roughly tied with complexity metrics, and in their cross-release Naive Bayes setup (2.0 and 2.1 predicting each other) network metrics alone were worse on every averaged measure (Table 5). So the answer to the theme question is: the network-metric advantage has not been shown to survive realistic cross-version evaluation; the best available evidence (Premraj & Herzig) shows parity, not superiority.

None of the seven papers measures or controls duplicate or unchanged modules across versions or splits. In random within-release splits, inter-module graph features are computed on the full graph and are highly correlated among neighbouring or similar modules. In forward-release setups, unchanged files carry identical code metrics and near-identical network metrics from training to test. Neither effect is quantified anywhere in this group. Premraj & Herzig's contrast (strong random-split gain that disappears forward) is consistent with, but does not prove, an instance-similarity or leakage explanation. Quantifying it is exactly the project's gap.

The learned-embedding and GNN line (node2defect 2018, GCN2defect 2021, DeMuVGN 2024) does not engage with the Premraj & Herzig result. node2defect and GCN2defect could only be assessed from abstracts: both report F-measure gains only (9.15%; 6.84-23.85%), with split types unverifiable. DeMuVGN, the only one read in full, uses transductive within-version random node splits and cross-project transfer but never within-project cross-version prediction, despite having 5 ActiveMQ versions. Its developer view is built from defect-report assignees, a plausible label-leakage path. Its reported F1 values are internally inconsistent with its recall values (e.g. HBase-0.95.0 recall 0.605 with F1 0.993, where the maximum attainable is 0.754), and the preprint has been withdrawn by its authors. Bryan & Moriano (2023), in the JIT setting, use a random non-chronological split and a whole-history graph. Their 152% F1 gain shrinks to +3% MCC (0.5141 to 0.5316, Table 4) against a baseline apparently quoted rather than re-run. The more sophisticated the graph model, the weaker the evaluation protocol in this group.

Recurring weaknesses: single-release or single-pair evaluations with low statistical power (Z&N: 1 release; Premraj & Herzig: 3 forward pairs; Tosun: 2 Eclipse releases); threshold-dependent measures (precision, recall, F1, pd/pf) with fixed or test-optimised thresholds, and MCC only in Bryan & Moriano. No effort-aware measures (Popt, recall@20% LOC) in any paper. Weak code-metric baselines (8 metrics in Premraj & Herzig) or untuned ML baselines (DeMuVGN's SVM F1 ≈ 0). Resampling (SMOTE or SMOTETomek) is applied in all three GNN/embedding papers. Proprietary data in Z&N. All studies are Java or C/C++; none uses Python.

Open gaps directly addressed by the project: (1) a leakage-controlled CVDP comparison of graph-derived features (here, Joern CFG+DDG per-function graphs, optionally aggregated with call-graph network measures) against code metrics (SonarQube) and text embeddings (doc2vec, CodeBERT), with unchanged and duplicate functions identified and either removed or reported separately; (2) reporting MCC, AUC and effort-aware measures with variance across many version pairs (22 Django and 5 ActiveMQ versions give far more pairs than any study here); (3) the first Python evidence; (4) a check of whether any graph gain under random splits collapses under forward-release splits, as Premraj & Herzig found for network metrics. Note also that intra-procedural CFG/DDG graphs differ from the inter-module dependency networks studied here: the network-metric literature tells us about the module-interaction signal, not about function-internal structure, so these results set expectations but do not settle the project's question.
