# Graph-based SDP and code-graph foundations — reading notes

Access summary: full text read for BugPre, MFGNN (JSS 2021, arXiv version), Allamanis et al. 2018, Devign (arXiv v1), GraphCodeBERT. Abstract-only (closed access, no preprint found): CFG2AT, MVHR-DP (plus repository README), SeDPGK, Code Property Graphs (Yamaguchi 2014). Numbers for abstract-only papers are provisional.


## Liu H., Zhang H., Liu J., Li Z. et al., 2024, CFG2AT: Control Flow Graph and Graph Attention Network-Based Software Defect Prediction, IEEE Transactions on Reliability
DOI: 10.1109/tr.2024.3503688 — access: **abstract_only**

- **Task / granularity:** Software defect prediction (binary). Granularity not stated in the abstract (likely file level on PROMISE-style data; unverified).
- **Language / data:** Abstract: '15 versions of six different open-source software projects'. Language, project names, instance counts and defect ratios not available (closed access; no preprint found).
- **Representation:** Control flow graph per program unit, processed by a 'graph-structured attention unit' (abstract). CFG construction tool, node features and edge types not available.
- **Model:** Graph attention network over CFGs (abstract). Architecture details not available.
- **Baselines:** 'a range of competing methods' (abstract); identity not available.
- **Evaluation setup:** Within-project defect prediction (WPDP) and cross-project defect prediction (CPDP) per the abstract. Whether WPDP means cross-version or random split, and whether resampling was applied, is not available.
- **Duplicates / leakage:** Not available (abstract only).
- **Key results:** Abstract only: relative improvements of 7.09–12.80% F1, 1.30–4.15% AUC, 6.78–17.54% MCC under WPDP; 23.76–44.79% F1, 8.93–13.27% AUC, 36.92–94.89% MCC under CPDP. These are relative gains over unnamed baselines; no absolute values or strongest-baseline numbers available.
- **Stated limitations:** Not available (abstract only).
- **Critical assessment:** Cannot be assessed beyond the abstract. Reports MCC and AUC, which is better than F1-only. Very large relative MCC gains under CPDP (up to 94.89%) usually indicate low baseline MCC, so absolute values matter. Code/data availability unknown. Information is provisional because the full text was not read.
- **Relevance to project:** Closest in spirit to a CFG-only arm of the project (CFG + GAT). Useful as a named CFG-GNN baseline design, but cannot be reproduced or compared on numbers without the full text. The user should obtain the PDF via institutional access to check its split type and whether WPDP is cross-version.

## Qiu S., Huang M., Liang Y., Peng C., Yuan Y., 2024, Code Multiview Hypergraph Representation Learning for Software Defect Prediction (MVHR-DP), IEEE Transactions on Reliability 73(4):1863–1876
DOI: 10.1109/tr.2024.3393415 — access: **abstract_only**

- **Task / granularity:** Software defect prediction. Per the public repository README (not the paper), nodes are classes in a class-dependency network, so class/file level.
- **Language / data:** README (not paper): ten open-source Java projects, 29 versions in total. Instance counts and defect ratios not available.
- **Representation:** Abstract: a hypergraph per 'code view', fused into one hypergraph. README (not paper): node features are 20 Understand static code metrics, 17 complex-network metrics, and ProNE network-embedding vectors. Class dependency network from DependencyFinder. Hyperedges join several classes. No CFG/DDG; this is an inter-module dependency graph.
- **Model:** Hypergraph neural network (hyperedge convolution) over the fused multi-view hypergraph (abstract and README).
- **Baselines:** 'baseline approaches' (abstract). Repository hosts full comparison PDFs for WPDP/CVDP/CPDP; not read.
- **Evaluation setup:** Within-project, cross-version and cross-project tasks (abstract; README provides run_WPDP/run_CVDP/run_CPDP scripts). Split details, resampling and runs are not available.
- **Duplicates / leakage:** Not available (abstract only).
- **Key results:** Abstract: 'superior' AUC, F-measure and MCC over baselines in WPDP, CVDP and CPDP. No numbers available.
- **Stated limitations:** Not available (abstract only).
- **Critical assessment:** Code and processed data are public (github.com/insoft-lab/MVHR-DP), which favours reproducibility. Because the graph is a project-level dependency network, hypergraph learning is likely transductive: test-version classes share graph structure with training classes. This is a leakage risk worth checking in the code. Inputs are dominated by classic metrics, so gains may reflect metrics plus network context rather than code semantics. Assessment is provisional.
- **Relevance to project:** Different graph type (module-dependency hypergraph, not per-function CFG/DDG). Relevant as a complementary 'context' view that could be combined with per-function graphs. It also shows how Understand/SonarQube-style metrics can serve as node features. Its CVDP scripts could be checked for how unchanged classes are handled.

## Wang Z., Tong W., Li P., Ye G., Chen H., Gong X., Tang Z., 2023 (online 2022), BugPre: an intelligent software version-to-version bug prediction system using graph convolutional neural networks, Complex & Intelligent Systems 9:3835–3855
DOI: 10.1007/s40747-022-00848-w — access: **full_text**

- **Task / granularity:** Cross-version defect prediction (CVDP) at method level. The model is trained on the prior version and predicts only on changed and change-impacted functions of the next version (Sec. System overview; Prediction).
- **Language / data:** Java only. Dataset 1 (Hadoop, Lucene, Log4j, Ant; 2 versions each) for AST-pruning study (Table 7). Dataset 2 (NanoXML, JUnit, HttpCore, Heritrix; 3 releases each) for change-impact analysis (Table 8). Dataset 3: PROMISE, 6 projects/20 releases (Camel, Ivy, Log4j, Xalan, Lucene, Ant), 109–1066 files per release, defect rates 3.3%–48.2% (Table 5). Dataset 4: Kafka (2.5.0, 2.6.1, 2.7.0) and Druid (0.19.0, 0.20.0, 0.22.1). Threshold calibration on Camel 1.4/1.6, Ant 1.5/1.6, Xalan 2.4/2.5. E.g., Camel has 357 changed vs 4651 unchanged function pairs (Table 3).
- **Representation:** Per-method graph built on the JavaParser AST (MethodDeclaration as root). Edge types: NextToken (AST child), NextExec (control flow added by three rules for if, loops and sequence), VarDefinition, VarUse and VarModify (data-flow). Calls appear only as a node feature, not as edges (Sec. AST-based node relationship construction). Node features: 8 statistical features (in/out degree, #method calls, isControlNode, is_Compare, isDeclaration, isAssignExpr, isBinaryExpr; Table 1) plus 6 version-change features (NR, NDC, NML, NDPV, MTPV, IBPV; Table 2). A separate Variable Propagation Tree (class, field, method and statement nodes with control, data and call edges) is used for change-impact analysis, not as model input.
- **Model:** GCNN with an iterated node update h_v(t+1) = tanh(W x_v + sigma(sum of neighbour states)), where sigma is an n-layer ReLU MLP, and a softmax output (Eqs. 1–3). Hyperparameters not reported.
- **Baselines:** LR, Transfer Naive Bayes, SVM and Decision Tree on PROMISE metrics (Fig. 9). DBN and TCNN on AST token vectors (Fig. 10). Prior CVDP approaches DS3, WGNCS and HALKP (Table 9), plus CPDP method ADCNN. The paper does not say whether the Table 9 numbers were re-run or copied.
- **Evaluation setup:** Cross-version: train/validation 8:2 split within the older version, test on the adjacent newer version (Sec. Efficiency of defect detection based on GCNN, e.g., Camel 1.0 to 1.2). The test set is restricted to changed functions (AST-pruned graph matching plus GumTree) and VPT-impacted functions. Labels: commit-message keywords ('fix', 'defect', 'bug') for self-collected data. Dataset 3 uses PROMISE file-level labels, and the paper does not explain how they are mapped to method-level graphs. No resampling reported; single run, no variance.
- **Duplicates / leakage:** Not framed as leakage. However, the design excludes unchanged functions from the test set: only changed and impacted functions are predicted, for efficiency. This removes the main cross-version duplicate source in the test set (as a side effect, not a stated control). Baselines in Table 9 were presumably evaluated on full releases, so the comparison is not like-for-like. Training data is not de-duplicated. The change-detection rule text says a pair whose similarity is 'greater than the threshold' is considered changed, which reads inverted (Sec. Obtaining change set).
- **Key results:** PROMISE (Fig. 9): GCNN average precision 67.5% (5.7–22.3% above four ML methods), average recall 71.8% (about 20–30% higher). DBN/TCNN averages are above 57% precision and 59% recall (Fig. 10 text). Table 9 average F1: BugPre 0.6721 vs WGNCS 0.4986 (strongest prior baseline), HALKP 0.4483, DS3 0.3708. F1 is 27% higher than ADCNN (text). AST pruning raises recall by 17.7% and precision by 2.6% on average (Fig. 6). VPT change-impact recall is about 95% for VPT, InfluenceCIA and VM-CIA, with VPT having higher precision (Fig. 8, Table 8). Only precision/recall/F1; no AUC/MCC; PofB20 explicitly not applicable (test is changed code only).
- **Stated limitations:** Keyword-based commit labelling is noisy. The system is Java-only and other languages need a parser. Insufficient early-version history (Sec. Limitation and discussion).
- **Critical assessment:** Weak evidence. F1/precision/recall only, no MCC/AUC or effort-aware measures, and no variance or statistical tests. Most results are in bar charts without tables. The test population (changed and impacted functions) differs from the baselines' (full release), which inflates comparability concerns. Method-level graphs are scored against PROMISE file-level labels without an explained mapping. The recall formula is misprinted as TP/(TP+TN). Table 9 labels the method 'DefectPre'. There is no code or data release and hyperparameters are not given. The threshold derivation is ad hoc.
- **Relevance to project:** High conceptual relevance. It is the only paper in this group that is explicitly CVDP at method level with CFG+data-flow graphs, and it embodies a 'changed-functions-only' test protocol. That protocol is effectively a deduplication-by-design, which the project can adopt as a leakage-controlled evaluation arm (evaluate on functions whose CFG/DDG or normalised AST changed between Django/ActiveMQ versions). Its edge schema (NextExec, VarDef/Use/Modify) maps onto Joern CFG + REACHING_DEF/DDG edges. Its process features (NR, NDC, NML, previous defects) are a reminder that history features may dominate; ablate them when comparing with doc2vec/CodeBERT/SonarQube.

## Zhao Z., Yang B., Li G., Liu H., Jin Z., 2021, Precise Learning of Source Code Contextual Semantics via Hierarchical Dependence Structure and Graph Attention Networks (MFGNN), Journal of Systems and Software (read via arXiv:2111.11435)
DOI: 10.1016/j.jss.2021.111108 — access: **full_text**

- **Task / granularity:** Program classification (CodeChef, Codeforces), file-level defect prediction (WPDP, CPDP on PROMISE) and functional clone detection (OJClone).
- **Language / data:** Defect prediction: PROMISE, 10 Java projects (lucene, synapse, xerces, xalan, camel, log4j, ant, jedit, poi, ivy). Mean files per version range from 70 (log4j) to 700 (camel), and defect rates from 10.3% (ivy) to 66.8% (poi) (Table 2). 1395 files dropped because Soot failed, and jedit 3.2 was not compilable (Sec. 4.2). Program classification uses C/C++, 9 problems, 2313–17379 instances (Table 1).
- **Representation:** Hierarchical graph. The outer level is an inter-procedural CFG over three-address IR (Soot/Jimple for Java, Clang/LLVM IR for C/C++) with data-flow edges from reaching-definition analysis. There are seven edge types: sequential, true, false and switch branches, call flow, exception flow and data flow (Sec. 3.1). The inner level gives each basic block its AST subtree, enriched with variable data types (camel-case split) and bitwise-split constants.
- **Model:** MFGNN: a modified TBCNN (depth-weighted) learns per-block local features. AGN4D, a GAT variant with forward and reverse graphs, edge-type-specific attention and skip connections over 3 layers of dim 200, learns contextual features. These are fused by sum, max-pooled and classified with logistic regression. AST embedding dim 50, Adamax, 200 epochs (Secs. 3.2, 4.3.1).
- **Baselines:** WPDP: AdaBoost, MLP and RF on PROMISE metrics; DBN with NB/LR/DT; TreeLSTM; DTL-DP (image-based); BugContext (CFG/DFG plus AST paths) (Table 4). CPDP: these plus TCA+, TNB and DBN-CP (Table 5). DBN, TreeLSTM, BugContext, TCA+ etc. were re-implemented.
- **Evaluation setup:** WPDP is cross-version: train on earlier version, test on next (e.g., ant 1.5 to 1.6; Table 4), 14 version pairs. CPDP uses 22 source-to-target pairs, with 30% of the target randomly used to fine-tune the LR classifier and prediction on the remaining 70% (Sec. 4.3.2). The CPDP setting is therefore partially supervised on the target. Labels are PROMISE file labels. The authors 'selected multiple groups of parameters randomly, ran all methods multiple times and kept the best result' (Sec. 5.2), i.e., best-of-N, with no variance reported.
- **Duplicates / leakage:** Duplicates removed only for the program-classification datasets (Sec. 4.2). Nothing on duplicates or unchanged files across PROMISE versions. The 30% target fine-tuning in CPDP is a disclosed target-data use.
- **Key results:** WPDP average (Table 4): MFGNN F1 52.9 / AUC 71.5; TreeLSTM 50.7/64.2; RF 46.4/68.2 (best metric baseline on AUC); AdaBoost 46.4/66.5; BugContext 42.0/53.6; DTL-DP 44.3/42.7. CPDP average (Table 5): MFGNN 55.2/70.3; TNB 48.9/68.4 (strongest baseline); RF 37.6/67.2. Program classification average (Table 3): MFGNN accuracy 71.5 / macro-F1 63.5 vs TreeLSTM 67.5/56.7 and DGCNN(0.4M) 66.5/55.4. Ablation (Table 7): CFG-only 70.3/62.4, DFG-only 68.7/59.7, BoW blocks 63.8/53.7. GAT-variant (AGN4D) beats GCN (68.9/58.6) and GGNN (68.7/57.8). The metric baseline RF is within 1.4 AUC points of TreeLSTM and 3.3 below MFGNN in WPDP.
- **Stated limitations:** Re-implemented baselines may not match the originals. Baselines were designed for other tasks. Some PROMISE versions are missing, so original data could not be used. CFGs differ across IRs (Jimple vs LLVM IR). The tasks and datasets are limited (Sec. 5.6).
- **Critical assessment:** Moderate-to-weak defect-prediction evidence. Best-of-N selection for all methods with no variance. F1 and AUC only (no MCC or effort-aware measures). Small per-version datasets (70–700 files). The dataset changed after the Soot failures dropped 1395 files, which may bias toward compilable code. No de-duplication across versions. CPDP uses target labels. Gains over a tuned RF on metrics are modest in AUC. No code release found in the text. The strongest evidence is the ablation on program classification, where AST-in-block versus BoW and CFG versus DFG are isolated.
- **Relevance to project:** High for graph design. It shows that representing CFG nodes (statements or basic blocks) with richer syntax beats bag-of-words node features. This is directly applicable to Joern per-function CFG+DDG, where node features could come from CodeBERT/doc2vec embeddings of statement code instead of BoW. It also suggests typed edges (control vs data) and both edge directions. Its cross-version WPDP protocol mirrors CVDP but without duplicate control, which is the project's gap. Being Java-only and dependent on compilation (Soot), it does not transfer to Python/Django, whereas Joern's source-level frontends do.

## Yamaguchi F., Golde N., Arp D., Rieck K., 2014, Modeling and Discovering Vulnerabilities with Code Property Graphs, IEEE Symposium on Security and Privacy, pp. 590–604
DOI: 10.1109/sp.2014.44 — access: **abstract_only**

- **Task / granularity:** Vulnerability discovery by graph-traversal queries (not machine-learned classification), C code.
- **Language / data:** Abstract and secondary snippets: C code; applied to the Linux kernel. Exact counts not available from what was read.
- **Representation:** Code property graph (CPG): merges abstract syntax trees, control flow graphs and program dependence graphs into one property graph with labelled edges and key–value node properties. It is stored in a graph database and queried with traversals (abstract and author talk slides). This is the data model behind Joern.
- **Model:** No learned model. Vulnerability templates are expressed as graph traversals (e.g., buffer overflows, integer overflows, format string vulnerabilities, memory disclosures; abstract).
- **Baselines:** Not available (abstract only).
- **Evaluation setup:** Not applicable/not available (manual review of traversal results).
- **Duplicates / leakage:** Not applicable.
- **Key results:** Not available from the abstract; no numbers reported here.
- **Stated limitations:** Not available (abstract only).
- **Critical assessment:** Foundational representation paper. The full text could not be retrieved: IEEE is closed, the author host returned 502/404 and no arXiv version exists. Claims here rest on the abstract and on how later papers (Devign) describe it. Devign cites it for the point that AST-only, AST+CFG and AST+CFG+PDG cover progressively more vulnerability types. That claim is second-hand here.
- **Relevance to project:** Direct: Joern produces CPGs, and the project's per-function CFG and DDG are projections of the CPG. A practical consequence is that AST, CFG, CDG and REACHING_DEF/DDG edges share one node set (Devign does exactly this). The project can therefore test AST-only vs CFG vs DDG vs combined graphs with identical nodes, which is a clean ablation.

## Allamanis M., Brockschmidt M., Khademi M., 2018, Learning to Represent Programs with Graphs, ICLR 2018 (arXiv:1711.00740v3)
DOI: 10.48550/arxiv.1711.00740 — access: **full_text**

- **Task / granularity:** VarMisuse (select the correct variable at a slot) and VarNaming (predict a variable name). Token/slot level within files; not defect prediction.
- **Language / data:** C#. 29 top-starred GitHub projects compiled with Roslyn, about 2.9M non-empty LOC (Sec. 5, Table 4). On average 3.8 type-correct candidates per slot (median 3).
- **Representation:** Program graph with the AST backbone (syntax nodes and tokens). Edge types: Child, NextToken, LastRead/LastUse, LastWrite, ComputedFrom, LastLexicalUse, ReturnsTo, FormalArgName, GuardedBy and GuardedByNegation. Each has a backward counterpart, giving 20 edge types (Secs. 4, 4.1). Node init averages subtoken embeddings of the name and concatenates a type embedding (element-wise max over supertypes). Graphs average 2,228 nodes (median 936) and 8,350 edges.
- **Model:** Gated Graph Neural Network: per-edge-type linear messages, sum aggregation, GRU update, 8 propagation steps, hidden size 64. VarMisuse inserts slot and candidate nodes and uses max-margin scoring; VarNaming uses graph2seq with a GRU decoder. Footnote: GCNs 'generalized less well than GGNNs'.
- **Baselines:** LOC (2-layer BiGRU over local tokens) and AvgBiRNN (averaged BiRNN over all usages) for VarMisuse. AvgLBL (log-bilinear) and AvgBiRNN for VarNaming.
- **Evaluation setup:** 2 projects for development and 3 projects held out entirely (UnseenProjTest). The remaining 23 projects are split 60/10/30 by file (SeenProjTest). Results averaged over two runs (Table 1 caption); published-subset results over three runs (App. D).
- **Duplicates / leakage:** Duplicates are not discussed. The paper explicitly separates seen-project (file-level split) and unseen-project tests. The drop from seen to unseen (VarMisuse 85.5 to 78.2; VarNaming 53.6 to 44.0) is attributed to unknown type hierarchy and vocabulary (Sec. 5.1). This is direct evidence that within-project splits overestimate generalisation.
- **Key results:** Table 1, VarMisuse accuracy: GGNN 85.5% seen / 78.2% unseen vs AvgBiRNN 73.7 / 60.2 (strongest baseline). PR-AUC 0.980 / 0.958 vs 0.941 / 0.895. VarNaming accuracy: 53.6 / 44.0 vs AvgBiRNN 42.9 / 23.4. Note the text claims 32.9% VarNaming accuracy in Sec. 1, which contradicts Table 1. Ablation (Table 2, VarMisuse/VarNaming): syntax edges only 55.3/34.3; semantic edges only 78.4/52.9; NextToken+Child+LastUse+LastWrite 80.6/31.2. Published-data rerun (App. D): 84.0 / 74.1 accuracy. Practical bugs: 3 found in RavenDB and 3 in Roslyn among top-500 reviewed locations (Sec. 5.3).
- **Stated limitations:** Requires compilable code and type information. Generalisation to unseen projects is harder because of unknown types and vocabulary. Interprocedural reasoning is missing (App. B sample 5).
- **Critical assessment:** Strong, influential and reproducible: a generic GGNN implementation and the dataset (minus GPL projects) are released. Two to three runs, no variance shown. The task is synthetic, since the label is the original variable and real misuse bugs are rare, so it is not defect prediction. The abstract/introduction vs Table 1 inconsistency for VarNaming should be noted when citing. There is no deduplication across files despite GitHub code being highly duplicated (cf. Allamanis 2019).
- **Relevance to project:** Foundational for the model choice. Typed, bidirectional data-flow edges (LastRead/LastWrite/ComputedFrom) mattered more than syntax-only edges for a bug-related task. GGNN with per-edge-type messages is a sensible default for Joern CFG+DDG graphs, and adding reverse edges is cheap. The seen-vs-unseen project protocol is a template for reporting both within-project cross-version and cross-project (Django to ActiveMQ is cross-language, so harder). It relies on types, which Python/Django lacks, so expect weaker node-type information there.

## Zhou Y., Liu S., Siow J., Du X., Liu Y., 2019, Devign: Effective Vulnerability Identification by Learning Comprehensive Program Semantics via Graph Neural Networks, NeurIPS 2019 (read arXiv:1909.03496v1 preprint)
DOI: 10.48550/arxiv.1909.03496 — access: **full_text**

- **Task / granularity:** Function-level binary vulnerability classification.
- **Language / data:** C. Linux Kernel, QEMU, Wireshark, FFmpeg. 48,687 security-related commits (23,355 VFCs). 58,965 function graphs, of which 27,652 are vulnerable (about 46.9%) (Table 1). Labelling took 600 man-hours by four security researchers (Sec. 3.1). Functions with more than 500 nodes were removed (15%).
- **Representation:** Joint graph on the Joern AST node set (Sec. 2.2.2, 3.1). Edge types: AST, CFG (from Joern), three data-flow edges replacing variable-labelled DFG edges (LastRead DFG_R, LastWrite DFG_W, ComputedFrom DFG_C, following Allamanis), and natural code sequence (NCS) edges between AST leaves. Node features: word2vec (dim 100) embedding of the node's code concatenated with a label-encoded node type.
- **Model:** Gated graph recurrent layers (6 time steps, hidden 200, SUM aggregation over edge types) followed by a 'Conv module': 1-D convolution plus max-pooling over node features, with and without the initial features, multiplied and averaged, then a sigmoid (Eqs. 3–9). Adam, lr 1e-4, batch 128.
- **Baselines:** Metrics+XGBoost (4 complexity and 11 vulnerability metrics from Joern, Bayesian-optimised), 3-layer BiLSTM, BiLSTM+attention, CNN. Ablations: Ggrn with flat summation readout, and single-edge-type graphs. Static analysers: Cppcheck, Flawfinder and an anonymised commercial tool (Table 3).
- **Evaluation setup:** Random shuffle and 75%/25% split per dataset into 'training' and 'validation' (Sec. 3.3). No separate held-out test set is described in v1. For the imbalanced experiment, the test data were randomly sub-sampled to 10% vulnerable functions (Table 3). A CVE study used 112 vulnerable functions from 40 recent CVEs (positives only).
- **Duplicates / leakage:** Not discussed. Random function-level split; vulnerable (pre-fix) and non-vulnerable functions come from commits and can share near-identical code. Multiple versions of the same function across commits can fall on both sides of the split. No deduplication is mentioned. Later work (ReVeal, Chakraborty et al. 2021) criticised this setting; not read here.
- **Key results:** Table 2, Combined: Devign (Composite) ACC 72.26 / F1 73.26; Devign (CFG only) 71.32/71.27; Ggrn (Composite) 70.35/69.37; BiLSTM+Att 69.57/68.65 (strongest non-graph baseline); Metrics+XGBoost 61.36/63.76. On Linux, Metrics+XGBoost F1 is 79.14 vs Devign 84.97. Reported average relative gains over baselines: +10.51% accuracy, +8.68% F1; the Conv module adds +4.66% accuracy and +6.37% F1 vs Ggrn. Imbalanced test (Table 3, Combined): Devign F1 27.25 vs CNN 17.94 and Flawfinder 10.41. CVE set: 74.11% 'accuracy', which equals recall because all items are positive.
- **Stated limitations:** Joern failed on some functions, which were filtered. Large functions were removed. Future work: program slicing for big functions, cross-project application, explainability (Secs. 3.1, 5).
- **Critical assessment:** Influential but methodologically weak by current standards. Evaluation is on a random split labelled 'validation' with no clear test set or variance. The balanced dataset (about 47% positive) is unrealistic; F1 collapses to 27 under 10% prevalence. There is no deduplication, and accuracy/F1 only. Single-edge-type graphs (e.g., CFG only) come within about 1 point of the composite graph on Combined, so the multi-graph benefit is small. Only two of four datasets (FFmpeg, QEMU) are released; code is not linked in the v1 text.
- **Relevance to project:** Very high for construction. It is the canonical Joern-based per-function joint graph (AST + CFG + data-flow + token-order edges, shared node set) with GGNN, which is exactly what the project builds. Copyable details: replace variable-labelled DDG edges with a small set of typed edges, use word2vec/code embeddings plus node type as node features, and cap graph size (report how many functions exceed it). Its weaknesses (random split, no dedup, balanced data) are exactly what the project's cross-version, duplicate-aware evaluation addresses. Report MCC and realistic prevalence instead.

## Guo D., Ren S., Lu S., Feng Z., et al., 2021, GraphCodeBERT: Pre-training Code Representations with Data Flow, ICLR 2021 (arXiv:2009.08366v4)
DOI: 10.48550/arxiv.2009.08366 — access: **full_text**

- **Task / granularity:** Pre-trained code representation, evaluated on code search, clone detection, code translation and code refinement (function level). Defect prediction not evaluated.
- **Language / data:** Pre-training: CodeSearchNet, 2.3M functions with documentation in six languages (Go, Java, JavaScript, PHP, Python, Ruby) (App. A). Downstream: filtered CodeSearchNet code search (e.g., Python 251,820 training examples; Table 7), BigCloneBench, Java-C# translation (11,800 method pairs after de-duplication), Tufano et al. refinement data.
- **Representation:** Variable-level data-flow graph extracted from the tree-sitter AST. Nodes are variable occurrences and edges mean 'where-the-value-comes-from' (Sec. 3). There are no control-flow edges. The input sequence is [CLS] comment [SEP] code [SEP] variables. A graph-guided attention mask lets variable nodes attend only along data-flow edges and to the code tokens they come from (Eq. 6). Max 512 tokens and 128 nodes.
- **Model:** 12-layer Transformer (768 hidden, 12 heads) initialised from CodeBERT. Pre-trained with masked language modelling, data-flow edge prediction (20% of nodes masked) and node alignment between variables and code tokens. 200K batches of 1,024; about 83 h on 32 V100 GPUs (App. A).
- **Baselines:** CodeBERT, RoBERTa, RoBERTa(code), task-specific models (e.g., ASTNN, FA-AST-GMN for clone detection; PBSMT and Transformer for translation).
- **Evaluation setup:** Standard benchmark splits per task. Code search adds a filtered dataset and retrieval over the whole dev/test corpus. A t-test against baselines (p<0.01) is reported for code search and clone detection. Seeds/variance are not shown.
- **Duplicates / leakage:** Duplicates removed for the code-translation pairs (App.). Nothing on BigCloneBench or CodeSearchNet duplication or on overlap between pre-training corpus and downstream test sets.
- **Key results:** Code search MRR overall 0.713 vs CodeBERT 0.693 (Table 1). Clone detection F1 0.950 vs CodeBERT 0.941 and FA-AST-GMN 0.95 (Table 2). Translation Java to C# BLEU 80.58 / accuracy 59.4 vs CodeBERT 79.92 / 59.0 (Table 3). Refinement accuracy small 17.3 vs 16.4, medium 9.1 vs 5.2 (Table 4). Ablation (Table 5): without data flow 0.693, without NodeAlign 0.703, without EdgePred 0.707. The 'w/o Data Flow' row is numerically identical to the CodeBERT row. Attention from [CLS] to variable nodes is 9.0–32.3% while nodes are 5.0–19.4% of the input (Table 6). AST injection hurt MRR at short sequence lengths (Fig. 4).
- **Stated limitations:** Not explicitly listed. Implicit: the Transformer's quadratic cost limits input length (Sec. 5.5).
- **Critical assessment:** Strong engineering with code and data released (github.com/microsoft/CodeBERT). Gains over CodeBERT are consistent but small (about 0.5–2 points on most tasks). BigCloneBench is known to be easy and leakage-prone, and clone F1 equals that of the non-pretrained FA-AST-GMN. The identical 'w/o data flow' and CodeBERT rows suggest the ablation may reuse CodeBERT rather than a re-pretrained variant without data flow. Data flow carries only def-use information, with no control flow.
- **Relevance to project:** High as a baseline. It is the natural 'CodeBERT + DDG' middle ground between the project's CodeBERT embeddings and Joern GNNs. It supports Python and Java (Django and ActiveMQ) out of the box. Its data-flow extractor is close to Joern's REACHING_DEF but omits CFG, so comparing GraphCodeBERT vs CodeBERT isolates the value of DDG under the same leakage-controlled CVDP splits. Caveats: the 512-token limit truncates long Django/ActiveMQ functions. Django/ActiveMQ code from GitHub may also overlap with the CodeSearchNet pre-training corpus, a pre-training leakage channel to discuss.

## Synthesis

This group spans two kinds of work. The first is foundational code-graph learning: the CPG data model behind Joern, typed program graphs with GGNNs (Allamanis 2018), Joern-based joint graphs for function-level vulnerability detection (Devign), and data-flow-aware pre-training (GraphCodeBERT). The second is recent graph-based defect prediction: BugPre, MFGNN/hierarchical dependence graphs, CFG2AT, MVHR-DP and SeDPGK. On the representation side the read papers agree. Explicit semantic edges add signal beyond syntax-only structure. Allamanis' ablation drops VarMisuse accuracy from 85.5 to 55.3 with syntax edges only (Table 2). GraphCodeBERT loses 2 MRR points without data flow (Table 5). MFGNN's ablation shows CFG-only beats DFG-only overall, but richer node content (AST subtrees instead of bag-of-words) matters more than which edges are present: 63.8 to 71.5 accuracy (Table 7). Devign likewise finds single-edge-type graphs within about 1 point of the composite graph on the combined dataset (Table 2). Together these suggest node features and data-flow edges carry most of the gain, with the full CPG adding little.

The defect-prediction evidence is much weaker than the representation evidence. Among the two SDP papers read in full, MFGNN reports average cross-version F1 52.9 / AUC 71.5 vs a metric-based RF at 46.4 / 68.2 (Table 4). It selects the best of several random hyperparameter runs for every method, reports no variance, and drops 1395 files that Soot could not process. BugPre reports average F1 0.672 vs 0.499 for the best prior CVDP method (Table 9). Its test set contains only changed and impacted functions while baselines see whole releases. It maps method-level graphs to PROMISE file labels without explanation and releases no code. Both use small PROMISE releases (roughly 70–1066 files per version), F1/AUC rather than MCC, and no effort-aware measures, statistical tests or de-duplication. The closed-access papers (CFG2AT, MVHR-DP, SeDPGK) could only be read at abstract level. CFG2AT and MVHR-DP report MCC and claim gains in cross-version or cross-project settings, but their split details and duplicate handling are unknown, so those claims are provisional.

No paper in the group treats duplicates or unchanged code across versions as a leakage threat in defect prediction. The closest are indirect. BugPre's changed-functions-only test protocol excludes unchanged functions from the test set as a side effect of an efficiency goal. Allamanis' seen- vs unseen-project split shows a 7–10 point accuracy drop when files from the same project cannot appear in training. Devign uses a random function-level split on commit-derived functions with no deduplication, a setting later critiqued (ReVeal) but not addressed in the paper itself. GraphCodeBERT de-duplicates only the translation pairs and says nothing about CodeSearchNet pre-training overlapping downstream data.

Design guidance that transfers to the project's Joern per-function CFG+DDG graphs:
1. Build all edge types on one shared node set, as in CPG and Devign, so AST/CFG/DDG/combined ablations differ only in edges.
2. Use typed, bidirectional edges and GGNN- or GAT-style per-edge-type messages. GCN underperformed in both Allamanis (footnote) and MFGNN (Table 7).
3. Give statement nodes rich content features, e.g., CodeBERT or doc2vec embeddings of the statement code plus the node type, rather than bag-of-words.
4. Cap and report oversized graphs; Devign removed the 15% of functions above 500 nodes.
5. Include GraphCodeBERT as the 'pretrained + DDG' baseline. It supports Python and Java and isolates the value of data flow against CodeBERT.

Open gaps this group leaves for the project:
1. Leakage-controlled cross-version evaluation of graph models: report results on all functions vs changed-only or de-duplicated functions (identical normalised code or identical CFG/DDG across versions).
2. Python. All read papers use Java, C or C#, and type-dependent features (Allamanis, MFGNN's Soot pipeline) do not carry over. Joern's source-level frontends are the practical route.
3. Strong non-graph baselines (SonarQube/Understand metrics with tuned RF, doc2vec, CodeBERT, GraphCodeBERT) evaluated with MCC, AUC and effort-aware measures over repeated runs. In the read papers, metric baselines were often close to the graph models: Devign Linux F1 79.1 vs 85.0; MFGNN AUC 68.2 vs 71.5.
4. Label granularity. File-level PROMISE labels applied to method-level graphs (BugPre) add noise, whereas the project's function-level labels avoid it.
